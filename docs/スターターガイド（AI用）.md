# Mittler スターターガイド（AI用：Claude Code・Codex など）

Mittler の作品制作を手伝う AI が読む説明書です（入口はリポジトリの根の `AGENTS.md`）。

- **読む順**：**このガイド → 作品の `AGENTS.md`（前からの作品は `CLAUDE.md`）→ 必要に応じて `docs/タイムライン形式.md`（ファイルの形）・`docs/エフェクトの書き方.md`（エフェクト）**
- **ユーザー向け画面・操作の案内**：`docs/スターターガイド（人間用）.md` を参照し、ユーザーに説明するときの言葉もそこに合わせます。
- **このガイドの正しさ**：このガイドとほかの文書は、完全な正しさを保証しません。作業中にコード・実際の動きとの不整合や誤りに気づいたら、調べて、誤りと分かったら何がどう間違っていたかをユーザーに伝えて確認し、**許可をもらってから**方針を変える・バグとして直します（根の `AGENTS.md` の「文書の正しさについて」）。

## 0. 作品づくりの進め方（「○○ってテーマで動画を作って」と頼まれたら、まずこれ）

「○○ってテーマでテクい動画を作って」と頼まれたら、エージェントが Mittler の全機能を把握して、技術的に凝っていて見ごたえのある（「テクい」）動画を作ることを目標にします。

Mittler の機能を理解し、組み合わせたり驚くような使い方を見つけたりしてクリエイティブを目指します。動画の中の 1 つの表現のために、Mittler の機能を複数検討してプランを立ててください。任せきりにすると機能の生かし方・理解・研究が足りなくなりやすいため、**動画を作る前に、まず機能の理解と研究を行います**。

### 5 段階の制作手順

> **この 5 段階の制作手順が最重要です。**
> 1. 素晴らしいプランを立てる
> 2. 動画の骨格を作る（キャラクター選び・曲の歌詞・動画化予定の設置・エフェクトの作成・素材の収集など）
> 3. H3 の動画と音楽の生成・採用をユーザーと行う（ここまでで、エフェクト以外の必要な素材がそろう）
> 4. 音ハメやリリック演出などを、画面を確かめながら AI が緻密に行う本格的な動画制作
> 5. ユーザーと最後の調整

> **曲と歌詞を渡されて MV を頼まれたとき**は、`docs/MVを作る（AI用）.md` の進め方（最初の質問 → 企画書と絵コンテの PDF → OK）が、下の手順 1 の「最初の確認」と「計画を見せる」の代わりになります。OK のあとは、下の 2〜5 で進めます。

#### 1. 素晴らしいプランを立てる

1. **最初にユーザーへ確認する（研究・プランに入る前）**
   - プランを作ったあとに見せるか、できたらそのまま進んでよいかを事前に聞き、答えのとおりに作業します。
     > 「プランができたら、① 見せて OK をもらってから作る／② そのまま進めてよい、のどちらにしますか」
   - **② を選ばれたら**、ざっくりの使用量（画像の生成の枚数・動画の本数・曲の生成の回数・TTS の許可）も**この最初の問いでまとめて聞きます**（プランのあとに止まらないため）。**① なら**使用量はプランと一緒に見せて確かめます。
   - 答えは作品の `work/research.md`（または計画のファイル）の先頭に書き残し、**その通りに作業します**（途中でユーザーが変更したら従います）。
   - ② でも、使用量の範囲を超えるとき・H3 の動画と Suno の曲の生成を頼むとき（手順 3）・Suno の採用は、従来どおりユーザーと一緒に進めます。

2. **画像生成エンジンを確認する（画像の生成を使う場合、同じ最初の問いで聞く）**
   - 「Codex・OpenAI（Image API）・Nano Banana（Gemini）のどれで作るか」を事前に聞き、答えをその作品の既定にします（下の「画像の生成と直し」の向き不向きも合わせて伝えます）。

   | エンジン | 仕組み・鍵 | 特徴・参照枚数 |
   |---|---|---|
   | `codex`（Codex） | Codex CLI | 作品の Codex の会話を続けるため絵がそろいやすい・参照 5 枚 |
   | `openai`（OpenAI） | Image API（鍵 `ps:OPENAI_API_KEY`・従量課金） | モデルと品質を選べる・参照 16 枚 |
   | `nanobanana`（Nano Banana） | Gemini の画像生成（鍵は Gemini TTS と同じ `ps:GEMINI_API_KEY`・従量課金） | モデルと解像度 `1K`／`2K`／`4K` を選べる・既定は Nano Banana Pro の 2K・参照 14 枚 |

   - 答えはタイムラインの `settings.image_engine`（`"codex"`・`"openai"`・`"nanobanana"`）に書き（作業のあとにコミット。4.5）、`work/research.md` の先頭にも書きます。これが**作品の既定**（絵の欄の `engine` が空のとき）です。既定を変えるのは、ユーザーが言ったときだけです。
   - **ほかのエンジンも呼べます**（作品の既定以外を断りません）。向き不向きで使い分けて構いません（生成は GPT Image 2.5、直しは Nano Banana Pro など）。絵の欄の `engine`・`model`・`quality` に書くか、1 回だけなら `api image … --engine nanobanana`・`api gen-image … --engine nanobanana` で指定します。使う量は計画の OK の範囲内とします（鍵の無いエンジンは使えません）。
   - 作品に `settings.image_engine` が無いまま画像を作ることになったら、作る前に聞きます（前からの作品も同じ）。

3. **まず機能を理解する（研究）**
   - 作り始める前に `docs/表現の一覧.md` を全部読み、使いそうな機能はくわしい文書まで読み込みます：
     - `docs/エフェクトの書き方.md`・`docs/タイムライン形式.md`
     - 下の 7.7 の 3D・7.56 と `docs/Suno受け渡し契約.md`
     - 7.54 の解析・7.55 の音ハメ
     - `docs/表現の一覧.md` の 2.5 のキャラとリファレンス・`docs/GeminiTTSの演技タグ.md`
   - 部品の置き場（`python .mittler/api.py . effects`）・作品にある素材とキャラ・その PC で使える道具（生成・解析・3D・Blender・TTS の声）を確かめます。
   - 分からない機能は小さく試します（静止画を数枚描いて見る・短く書き出す）。分かったことは作品の `work/research.md`（git に入らない）に書きます。

4. **テーマを読み解いて、見せ場（表現の狙い）を決める**
   - 何を感じさせたいか・どこで驚かせるか・どこで気持ちよくさせるかを決めます。

5. **1 つの表現ごとに、Mittler の機能を複数（2〜3 案以上）検討する**
   - 例「ロゴの登場」：その場で書く GPU の立体の文字（`gl3d` の `sc.text`。部品には無い）／Blender の金属のロゴ（`blender3d`）／重ね絵＋光（`sprite`＋`fm_light`）／字幕＋文字のショックウェーブ（`bfx_text_shockwave`）。
   - **機能を組み合わせる**・**驚くような使い方を探す**（本来の目的の外の使い方も考えます。`docs/表現の一覧.md` の 8.5「組み合わせの例」が発想のたねです）。今の機能で足りなければ、新しいエフェクトを Python で書くことも案に入れます（5）。

6. **試して比べてから決める**
   - 案ごとに静止画や短い書き出しで試作し、自分の目で比べます（見ていない絵で決めない）。選んだ案と理由を計画にまとめます。

7. **計画をユーザーに見せる**（最初の問いで ① のとき。② なら書き残すだけで進む）
   - 見せ場ごとの案（選んだもの・ほかの候補）・尺・使う機能に加えて、**ざっくりの使用量**（画像の生成の枚数・動画の生成の本数・曲の生成の回数（Suno は 1 回で 2 本できる。7.56）・TTS のセリフの数くらい）を出して OK をもらいます。
   - **OK の範囲の中なら、そのあとは一言聞かずに自由に使って構いません**（範囲を超えるときだけ聞き直します）。
   - Gemini TTS は、ユーザーの事前の許可があれば好きなときに使ってよく、リトライもして構いません（`docs/GeminiTTSの演技タグ.md`）。
   - Suno の採用（ダウンロード用のクレジット）は従来どおり人が編集画面で押します。

#### 2. 動画の骨格を作る（AI が自走）

- キャラ選び・曲の歌詞（Suno の Custom＝歌詞つきで作れる。7.56）・動画化予定のクリップの設置（**画像の生成とその設置まで込みで自走してよい**）・エフェクトの作成・素材の収集・セリフ（TTS）などを行います。
- **生成（H3 の動画・Suno の曲）を頼む前に、それ以外の下準備は全部終わらせます**。

#### 3. H3 の動画と曲（Suno）の生成と採用を、ユーザーと一緒にやる

- H3 は Colab の許可ボタン、Suno の採用はクレジットの OK を人が押します。ここまででエフェクト以外の必要な素材がそろいます。

#### 4. 本格的な制作（AI が緻密に）

- 音ハメ（7.55）・リリックの演出（Suno の歌詞の時刻＝採用で入る kind `lyrics` のメタデータ・解析の文字起こし）・人物の切り抜きとマスク（7.54）・生成した動画の加工（歓迎される作業）などを、**画面で確かめながら**丁寧に進めます。
- 確認手段：静止画・プレビュー・編集画面の「オート」（AI が直した所へ再生位置が飛ぶ）・`python .mittler/api.py . ui …`（見せたい所を出せる）。
- 生成した動画と曲から取る拍・歌詞の時刻・人物のマスクの演出は**動画の見せ場**なので、時間をかけて丁寧に行います。

#### 5. ユーザーと最後の調整

---

### 制作の原則と表現のルール

- **心がけ**：1 つの表現を 1 つの機能で済ませず、ありきたりで終わらせないこと。Mittler ならではのもの（拍と音ハメ・3D・生成・解析・AI と人のやりとり）を生かします。ただし、最後はテーマに合っていて伝わることが一番です。
- **リリック動画の文字は、フォントだけの表現を最優先する**：
  - 特に理由がなければ、歌詞の後ろに帯・座布団・箱・半透明のマット・ぼかした背景を敷きません。
  - 読みやすさは、書体・太さ・大きさ・字の置き場所（絵の空いた所・人物のマスクの後ろ）・縁取り・影・光・色・字の動きで作ります。
  - 背景を敷くのは、ユーザーに頼まれたとき・その作品の意匠として決めたとき（理由を `work/research.md` に書く）だけです。
- **モーショングラフィックスで、イージング無し（等速の直線の動き）は禁止。すべての動きに緩急をつける**：
  - 文字・図形・ステッカー・カメラ（寄り・パン）・3D・HTML のレイヤー・パラメータの鍵の「出る・動く・止まる・消える」の全部に、イーズイン・アウト（cubic・expo・back・elastic・バネなど）をつけます。
  - キビキビ出てふわっと止まる・ため→はじける・行き過ぎて戻る など、動きの意味に合う緩急を選びます。ゆっくりした流れ（背景のドリフト・スクロール）も、始まりと終わりと速さのゆらぎに緩急を入れます。
  - エフェクトを書くときは、時刻 `t` をそのまま位置にせず、イージングの関数を通します（`mittler.helpers` の `smooth`・`ease_out_back`、GPU の 3D の `ease_out`・`back_out` など。足りなければその場で書きます。`docs/エフェクトの書き方.md`）。静止画を何枚か並べ、プレビューでも動きを確かめます。
- **字幕・リリックには、テーマに合った魅力的な OFL（SIL Open Font License）の書体をダウンロードして使う**：
  - 既定の書体（Noto Serif JP・Windows の書体）のまま済ませません。テーマ・曲・場面に合うものを何案か選んで、静止画で比べて決めます（見出し・歌詞・小さな字で書体を変えて構いません）。
  - 入手先は Google Fonts（`https://github.com/google/fonts` の `ofl/` が元のファイル）など、OFL と明記されたものです。**使う前に、そのページ・同梱の `OFL.txt` でライセンスが OFL かを確かめます**。
  - 日本語の歌詞なら、使う字が全部入っているか（かな・漢字・記号）を確かめます。置き場は作品の `assets/fonts/`（ライセンスの文 `OFL.txt` も一緒に置きます）。
  - どの書体をどこから取ってどこに使ったかを `work/research.md` に書きます。ダウンロードは道具（curl・WebFetch など）で行い、ブラウザで外のサイトを開きません。
- **画像の生成と直し（エンジンの使い分け）**：
  - **画像の生成は GPT Image 2.5（OpenAI の `gpt-image-2.5-sunburst`）、画像の編集（部分の修正）は Nano Banana Pro（Gemini 3 の `gemini-3-pro-image`）が優れます**。
  - Codex や GPT Image で、できた絵にさらに直しを重ねてかけると、細部が強調されすぎたノイズが生まれます（直すたびに悪くなります）。
  - そのため、できた絵の部分の修正は次のどちらかで行い、直した絵をまた直して…と重ねません：
    1. **Nano Banana Pro で直す**（直したい絵を参照に渡して、直す所だけを文で頼む）
    2. **直した絵を参照にせず、元のリファレンス（キャラの立ち絵・最初の参照・基準の全景）を参照し直して作り直す**
  - 0 の最初の問いでエンジンを聞くときも、この向き不向きをユーザーに伝えます（作品の既定 `settings.image_engine` のほかに、直しは `--engine nanobanana` などで呼べます）。
- **生成した絵は、必ず読み戻して確かめる**（画像の生成のたび。動画化予定の始まり・終わりの絵、素材、モック、サブエージェントが作った絵のどれも）：
  - 出力したファイルを開いて自分の目で見ます（見ていない絵は使わない）。参照・基準の全景・前後のカットと並べます。
  - **人物の配置**：頼んだ人数・位置・大きさ・構図か、参照どおりの人物（顔・髪・服）か、画面の外に切れていないか、字や要素と重なっていないか。
  - **手と指**：手を 1 つずつ拡大（切り抜き）して指の本数を数えます（縮小した絵では 6 本指などを見逃します）。手の数・腕の数、持っている物の持ち方も見ます。
  - **向き**：顔・体・視線の向き、左右（右手・左手、持ち手、髪の分け目や服の打ち合わせ、左右が反転していないか）、頼んだ向き（カメラを見る・横を向くなど）か。
  - まちがいがあれば使わずに作り直します（部分の修正は上の「画像の生成と直し」のとおり）。確かめたこと・作り直した理由は `work/research.md` に書きます。動画化予定の絵のまちがいは、生成した動画にそのまま引き継がれるので、特に念入りに。
- **画像の生成は多用してよい（むしろ使う）**：
  - 画像の生成は軽いため、ユーザーが許可していれば（0 の最初の問いの使用量。枚数は大きめに見積もってよい）、動画化予定の始まり・終わりの絵だけでなく、**部分的な素材**にも積極的に使います：フィルムグレイン・テクスチャ・光の漏れなどの重ねる絵、一部だけ動かす（切り抜いて揺らす・パララックスにする）ための絵、エフェクトの中で使う絵（パーティクルの形・3D の板やカードの面・背景の模様）、ロゴ風の飾り・小物など。
  - **作り方**（動画化予定に限らない 1 枚。編集画面は不要。上書き禁止）：
    ```
    python .mittler/api.py . gen-image assets/images/gen/<名前>.png --prompt "…" [--ref <絵>]… [--size 1024x1024] [--background transparent]
    ```
    - エンジンは `--engine` → 作品の `settings.image_engine`（上の手順 1）の順で決まります。
    - `--size`・`--background transparent`（透明の PNG）は OpenAI だけです。Nano Banana は `--size` を近い縦横の比にし、`--quality 1K|2K|4K` で解像度を指定し、透明にしたい場合は単色の背景で頼みます。
    - どのエフェクト・クリップで使ったかを `work/research.md` に書きます。
  - **ヒント**：
    - **一度に全部作らなくてよい**：その作業（エフェクトを組む・3D の面を作る・場面を詰める）に合わせて、要るときに要るものを都度作ります。作って画面で確かめ、足りなければ足す・作り直します。
    - **素材の生成と収集はサブエージェントに任せる**（可能な場合）：何枚も作る・効果音や参照を集めるなどを任せると、本体は組み立てと画面の確認に集中できます。依頼時は、作品のフォルダ・`settings.image_engine`・置き場と名前の決まり（`assets/…/gen/`、上書きしない）・欲しいものの文と参照・使い道を全部渡し、できたものの一覧（パスと中身）を返してもらいます。サブエージェントが作ったものも、本体が絵を見て確かめてから使います。
- **画面まるごとのモックでデザインを決める**：
  - デザインがキマらないときは、画像の生成で画面まるごとのモック（完成した 1 コマの見本）を作って見て構いません。
  - 何案か作って比べていいものを選び、その構図・配色・文字の組み方・質感を**動画のプロジェクトの中で（エフェクト・クリップ・生成した部品で）再現します**（モックの絵をそのまま貼って済ませない）。
  - モックは `work/mock/` に置きます（`gen-image work/mock/<名前>.png …`）。
- **3D は場面になじむよう慎重に調整する**：
  - **3D は、そのままでは極めてチープに見えやすいため、場面になじむように慎重に調整するのが必須です**。
  - 既定の値のまま置かず、色と明るさを場面に合わせる（色の手直し・光の向きと色・環境光）、質感（素材の色・つや・テクスチャに生成した絵）、被写界深度やぼかし・モーションブラー、影や映り込み・光のにじみ（ブルーム）、粒子・グレインで画面となじませる、動きの速さとイージング・カメラの揺れを調整します。何コマも静止画で確かめ、浮いて見えるなら直します（7.7）。
- **変わらない決まり**：
  - **開いている作品を直接直す**（4 の頭）・作業のたびにコミット（プッシュはしない。4.5）・素材を上書きしない。
  - 人の操作が要ったものは、Suno の採用と H3 の生成のほかは全部 `python .mittler/api.py . <コマンド>` で頼めます（7.53）。
- **重い処理と見張り（watchdog）**：
  - **重い処理は必要なら遠慮せず回して構いません。その代わり毎回、見張りを独立に立て続けます**。重いシーンの描画・書き出し・マスター・Blender・解析・まとめての生成では、画質・長さを勝手に落としません。
  - 回す前に長さを見積もり、**常にサブエージェント（または背景のタスク）で独立に** `tools/watchdog.py` を動かし、処理時間・GPU・メモリ・CPU を見張ります（見張りなしで回さない）。
    - 自分で起動する処理：`python <mittler>/tools/watchdog.py --expect-min <分> --log work/watch.log -- <コマンド>`
    - 書き出し・マスター：`-- <コマンド>` の代わりに `--on-stop "python .mittler/api.py . export-cancel"`
    - 動いているプロセス：`--pid`
  - 監視項目は経過時間・CPU・メモリ・コミット（スワップ込み）・GPU です。想定の 2 倍を超えた長さ・メモリ 95% が 30 秒・スワップの爆増・進まないまま全力（`--progress`）を検知すると停止します（終了番号 `3`）。
  - **異常で止まったら**：コードを確かめて直す → 小さく試す → 見張りを付けて回し直します。**直せなければ止めたまま、ユーザーに理由と記録を見せて許可をもらいます**（毎回）。止めるのは自分が起動・依頼したものだけです。

## 1. 全体の形

```
VS Code（拡張 extension.js）── *.cut.json を開く ──▶ server/server.js（127.0.0.1、書き込みと副作用のある GET はトークン付き。インストールガイド 11）
   │ 編集画面 editor/（素の HTML・JS。タイムラインを書くのはここだけ）    │
   │                                                                     ├ /api/timeline（読む・保存）・/api/events（変更通知）
   │                                                                     ├ /api/frame（止めた1コマ）→ server/pyrender.js → 描画サーバー `python -m mittler serve`
   │                                                                     ├ /api/export（書き出し）→ `python -m mittler video`（区間に分けて並列）
   │                                                                     ├ /api/tts → tools/tts_gen.py（Gemini TTS／VOICEVOX）
   │                                                                     ├ /api/jobs → work/jobs/ → tools/jobs.py（動画化予定の画像は Codex、動画は H3 のキュー tools/h3_jobs.py）
   │                                                                     ├ /api/analyze → 解析用の python（設定 mittler.analysis.python）で pyengine/mittler/analyze.py（解析）
   │                                                                     ├ /api/music（Suno の曲の受け取り口。server/music.js。Suno を呼ぶのは Claude Code だけ）
   │                                                                     ├ /api/video_audio（動画の音を WAV に）・/api/wave（波形）・/api/still（PNG）
   │                                                                     ├ /api/new_project（「＋ 新規」。tools/new_project.js の create() を呼ぶ）
   │                                                                     └ /api/assets・/api/thumb・/api/file（effects/*.py と characters.json だけ）
```

- **起動時の生成ファイル（`server/project_env.js`、1.5）**：
  - サーバーが起動すると、作品の `.mittler/server.json`（ポート・トークン）を書き出します。`tools/mittler_api.py`（Claude Code から頼む入口）はこれを読み込みます。
  - 同時に、その PC 用の `.mittler/env.json`（Mittler の場所・描く python）・`guide.md`（このガイドの写し）・中継 `hook.py`／`api.py`／`engine.py` も書き出します。
- **編集画面（`editor/`）の主なファイル**：
  - `ui.js`（見た目の土台：テーマ・知らせ・押せない理由）・`newproject.js`（「＋ 新規」）・`editor.js`（タイムライン・選ぶ・ドラッグ・キー）
  - `cutedit.js`（カット編集の道具）・`cutmeta.js`（カットの段＝メタデータを直す道具）・`media.js`（セリフ・字幕・音・トラック）・`plan.js`（動画化予定）
  - `warp.js`（映像の速さ・音ハメ・⟷ 伸ばす）・`assets.js`（アセット窓）・`analyze.js`（右クリックの解析）・`music.js`（Suno の曲）・`annotate.js`（書き込み）
  - `icons/`（アイコン。Lucide の SVG。出し方は `ui.js` の `MITTLER_ICON` と辞書の `{icon:名前}`）・`export.js`（書き出し）・`state.js`（今の状態を書く）
  - `calc.js`（編集画面とサーバーで同じ計算：warp の点・色の卓の式。Python との一致確認は `tools/smoke_same.py`）。解析の種類の一覧は `pyengine/mittler/analyze_kinds.json` の 1 か所です。
- **エンジン（`pyengine/mittler/`）の主なファイル**：
  - `engine.py`（1 コマ）・`serve.py`・`mix.py`（音）・`ass.py`（ASS の字幕）・`loudnorm.py`（音の正規化）・`onbeat.py`（音ハメ）・`master.py`（マスター書き出し）・`analyze.py`（解析）・`helpers.py`・`lib/`（作者の作品から取り込んだ部品）
- **描く PC と設定**：
  - 描く PC は常にサーバー（拡張）が動いている PC です。描く python は 設定 `mittler.render.python` → タイムラインの `render.python`（無ければ既定）→ `PATH` の `python` の順で探します（`pyrender.js` の `findLocal`）。
  - PC ごとの設定（`mittler.*`）と既定値（`server/defaults.js` の 1 か所）の一覧は `docs/インストールガイド.md` の 12 にあります。
  - ほかの PC（GPU のある PC など）で描くときは、VS Code の Remote-SSH でその PC に接続します（`docs/インストールガイド.md` の 10）。
- コードの配置やプロセスの関係は `docs/ARCHITECTURE.md` を参照してください。

  - 作品の `.claude/settings.json` のフック（UserPromptSubmit → `python -c` が作品の `.mittler/hook.py` を探す → Mittler の `tools/mittler_state.py`。前からの作品は `tools/mittler_state.py` を絶対パスで直接実行）が、話しかけられるたびに今の状態の要約を添えます。
  - **いちばん最近さわった編集画面が、会話している作品とは別の作品のとき**（VS Code の別のタブで別の作品を触っているとき）は、「いま手前は別の作品：<パス>」の 1 行とそちらの状態が添えられます（サーバーが一時フォルダの `mittler/recent.json` に記録。2026-11-14〜）。ユーザーの「これ」はそちらの可能性が高いため、直す対象もそちらの作品かユーザーに確かめます。
  - **ユーザーの「これ」「ここ」「この字幕」は、まずこの要約（足りなければ `state.json` と `current_frame.jpg`）で特定します。** 状態が古い（何分も前・閉じている）ときはその旨を伝えます。
- **画面への書き込み（アノテーション）**：
  - ユーザーが止めた画面にペン・矢印・丸・四角で描いて「AI に渡す」を押すと、`.mittler/annotations/<id>/` に保存されます：
    - `after.jpg`：書き込んだ画面
    - `before.jpg`：書き込み前の画面
    - `annotation.json`：時刻・コマ・線の範囲 bbox・線の種類と色・その時刻のクリップ・選んでいたクリップ

  - 次に話しかけられたとき、フックが「【✏️ ユーザーが編集画面で書き込んだ画面：…after.jpg】」を先頭に添えます（1 回だけ。添えたら `delivered: true`）。

  - 押すと、描いた画面の場所と短い頼みの文がクリップボードにコピーされます。ユーザーがそれをチャットに貼ってくることもあります。

## 3. 新しい作品

空のフォルダで「Mittler で新しいプロジェクトを始めたい」などと頼まれたら、`docs/新しい作品を始める（AI用）.md` のとおりに作成します（スキル `mittler-new-project` もそこを読みます）。

```
tools\mittler.cmd node tools\new_project.js <作品フォルダ> --title 表示名 [--width 1920 --height 1080 --fps 30 --duration 60] [--lang en|ja] [--no-git] [--json]
```

- **実行とバリデーション**：Node が入っていれば `node tools/new_project.js …` でも実行できます。`mittler.cmd` は引数を全部渡し、Node の終了番号を返します。幅・高さは偶数の整数、fps・長さは正の数でなければ作らずに断ります。
- **人が作る方法**：編集画面の上のバーの「＋ 新規」（`editor/newproject.js` → `POST /api/new_project`）または VS Code のコマンド「Mittler: 新しい作品を作る」を使います（どれも同じ `create()`）。
- **`--lang` オプション**：最初のトラック・メタデータの段の名前（字幕・映像・カット…）の言語を指定します。**ユーザーと話している言葉に合わせて渡します**（日本語で話していれば `--lang ja`。付けなければ英語）。`AGENTS.md`・`CLAUDE.md`・`README.md` はどちらでも日本語です。「＋ 新規」は画面の言語、VS Code のコマンドは設定 `mittler.language` で決まります。
- **生成される中身**：
  - `templates/project/` のひな形（空の `project.cut.json`・`characters.json`・`pronunciation.json`・`AGENTS.md`（作品の説明と決まり）・`CLAUDE.md`（それを読み込む入口）・`README.md`・`gitignore.txt`）
  - `effects_lib/common/` の `subtitle`・`sprite`・`fade`・`grade`
  - 空のフォルダ（`assets/images`・`videos`・`sfx`・`bgm`・`music`・`voice`・`fonts`・`characters`・`overlays`、`work/proxy`、`output`）
  - `.mittler/`（`env.json`・`guide.md`・中継。1.5）＋ git の最初のコミット
  - 作品のファイル（`AGENTS.md`・`CLAUDE.md`・`README.md`・`.claude/settings.json`・タイムライン）に Mittler の場所（絶対パス）は書きません（`tools/smoke_package.py` が確かめます）。
- **フォルダ名・前提の注意**：フォルダ名は英数字と `-` `_` のみにします（日本語のパスは道具の受け渡しで壊れたことがあります）。中身のあるフォルダには作りません。
- **`render` フィールドの扱い**：新しい作品のタイムラインには `render` を書きません（描く python は開く PC の設定か既定で決まります）。前の作品の `render.python` は確認のうえそのまま使います。前の作品に残る `render.host`・`render.remote` は使われません（サーバーがログに 1 度知らせるだけです）。

## 4. タイムライン（`*.cut.json`）を直すとき

- **ファイル形式**：`docs/タイムライン形式.md` の「Python エンジン（mittler/py1）」に従います。JSON は `indent=1`・`ensure_ascii=False`・末尾に改行（編集画面の保存と同じ）で書き出します。
- **ID とトラック順**：`id` は作品内で一意にします。`tracks` は**先頭がいちばん手前**（描画は下から＝処理の順）なので、新しいトラックはかけたい順の位置に入れます。
- **開いている作品を直接編集する**：
  - **ユーザーに明示的に別の場所を指示されない限り、Mittler（編集画面）で開かれている作品（タイムライン）を直接編集します**。写し（複製したプロジェクト・別のタイムライン）で作業すると、ユーザーが画面で AI の作業を確かめられなくて困るためです。
  - 開いている作品は、フックが添える編集画面の状態（1.6。`.mittler/state.json` の `timeline_file`）で分かります。
  - 頼まれた編集の作業は開いているタイムラインを直接直し、写しを使うのは Mittler 自体の確かめ（smoke など）と、ユーザーが「写しで試して」と言ったときだけにします（写しを作るときはユーザーに一言伝えます）。
  - 作業のたびにコミットします（戻せる印。プッシュはしない。4.5）。直したところは、編集画面の「オート」（上のバー。既定オン）で再生位置がそのクリップの真ん中へ飛んで光るため、ユーザーは画面で追えます。
- **編集画面との競合を避ける**：
  - 編集画面が開いていることが多いため注意が必要です。ファイルを書けば画面は自動で読み直しますが、人が画面で直している最中に書くと、あとから保存したほうが勝ちます。
  - **人が触っている最中は待ち、そうでなければ開いているものを直接**直します。大きく直す前に「今、画面で直していないか」をユーザーに確かめるか、終わったと言われてからにします（`state.json` の `unsaved` が `true` なら、編集画面がまだ保存していません）。
  - 外（エージェント）の直しを画面が読み直したあと、ユーザーが `Ctrl+Z` を押すと、**外の直しだけ**が戻って保存されます（画面に「外の直しを取り消した」と表示され、次の `Ctrl+Z` は自分の直し）。ファイルが想定と違うときは、まずユーザーが取り消したのではないかを確認します。
  - 画面が保存に失敗してやり直している間（「保存できなかった…」）は、外の直しを読み直しません。やり直しが通ると、画面の中身がファイルになります（外の直しは上書きされます）。
- **時刻の書き方（丸めない）**：
  - 編集画面は、コマに乗る時刻を `n / fps` の値そのまま（丸めない。例 `0.6666666666666666`）で書きます。ファイルで書くときも、コマに合わせたい頭・長さは `n / fps` を計算した値をそのまま書きます（`0.666667` のように 6 桁に丸めると、エンジンの `start <= t` の比較で 1 コマ遅れることがあります）。
  - 長さは「終わりのコマの時刻 − 頭」とし、頭＋長さが終わりのコマの時刻をこえないようにします。前からある丸めた値は、触らなければそのままにします。
- **テストは写しで行う**：
  - Mittler 自体の確かめ・smoke・壊れるかもしれない試しは、写し（`<名前>.test.cut.json`、git に入らない）か試しの作品で行い、ユーザーの正本のタイムラインでテストを流しません。
  - これは上の「開いている作品を直接編集する」と矛盾しません：頼まれた**作品づくりの直し**は開いている作品を直接、**テスト**は写しで行います（写しを作るときはユーザーに一言伝えます）。
- **色の値（`grade`・`tonemap`）**：頼まれない限り Claude が決めません（ユーザーが色の卓で決めます）。
- **編集画面の自動整合に合わせて保つ項目**（くわしくは `docs/タイムライン形式.md`）：
  - `link`：同じ印のクリップ（動画とその音など）は一緒に動かす・切る・消します。
  - `duration`：音以外のクリップを最後より後ろに置くと、編集画面は動画の長さをそこまで伸ばします。ファイルで置くときは `duration` も合わせます。
  - その他：`from_tts`・`from_tts_text`（セリフから作った字幕）、`delivery_style`（そのシーンの演技）、`video.seed`・`video.draft_steps`・`video.h3`（動画化予定のシード・下書き・H3 の設定）、メタデータの `from_analysis`（解析で入れたもの）、音のクリップの `music`（Suno の曲。テイク・採用待ちの印 `adopt`。下の 7.56）とメタデータの `from_music`・`from_suno`。

## 4.5 Claude の直しを戻せるようにする（作業のたびにコミット）

エージェントの直しを、あとからユーザーが見て・戻せるようにする決まりです（ステージングで止めず、作業のたびにコミットします。特に指示がなければ作業のたびにコミットし、ユーザーの指示があればそれに従います。プッシュはユーザーの指示がない限りしません）。

- **作業のたびにコミットする**：ユーザーに特に言われていなければ、作品のフォルダで `git add -A` → `git commit` します。作業の単位は 1 つの頼み、または大きな頼みの中の 1 つの区切り（場面を 1 つ組んだ・エフェクトを 1 本足した・カットを詰めた など）です。コミットメッセージは日本語で、何をしたか（直したファイル・クリップ・頼みの言葉）を 1〜2 行で書き、先頭に `AI:` を付けます。
- **始める前に `git status` を見る**：まだコミットしていない変更（ユーザーが編集画面で直した分など）があれば、先にそれだけをコミットします（`編集画面での直し（作業の前に記録）` など）。AI の直しと人の直しを 1 つのコミットに混ぜないことで、あとで AI の直しだけを戻せるようにします。
- **ユーザーの指示を優先する**：「コミットしないで」「まとめて 1 つに」「このメッセージで」などの指示があればそれに従います。
- **プッシュはしない**：ユーザーに頼まれたときだけプッシュします。
- **返事に記録を添える**：何を直したか（ファイル・クリップ）と、コミット（短いハッシュ）と、「戻すときは『戻して』と言えば、そのコミットを取り消す」を伝えます。
- **「戻して」と言われたら**：`git log` で該当の AI のコミットを確かめて `git revert <ハッシュ>`（取り消しのコミットを足す。歴史は消さない）を実行します。そのあとにユーザーの直しのコミットが重なっていてぶつかるときは、どうするかユーザーに聞きます。まだコミットしていない AI の直しは `git restore` します。編集画面は自動で読み直します。
- **素材は上書きしない**：素材（`assets/`・`work/`・`output/`）は git に入らない（`.gitignore`）ため、git では戻せません。必ず新しい名前で作り、前のものは残します。
- **git の無い作品（`.git` が無い）**：`git init` と最初のコミットをしてよいかユーザーに聞きます。

## 5. エフェクトを足す・直す（After Effects のエクスプレッション相当）

`effects/<名前>.py`（`STAGE`・`META`・`apply(ctx, f, clip)`）を書いて、タイムラインにクリップを置きます。くわしくは `docs/エフェクトの書き方.md` を参照してください。

- **決定論的であること（絵は時刻・コマ番号・マスクだけで決める）**：前のコマを覚えず、乱数は決まった種を使い、`hash(文字列)` は使いません。区間に分けた並列の書き出しでも同じ絵になるようにします。
- **処理速度とキャッシュ**：1 コマ数秒以内に収め、重い下ごしらえは `ctx.cache` を使います。
- **共通エフェクト（`effects_lib/common/`）と配布対象**：共通にしたいものは `effects_lib/common/` にも入れます。ただし新しい作品に配られるのは `tools/new_project.js` の `FIRST_EFFECTS`（`subtitle`・`sprite`・`fade`・`grade` の 4 本）だけです。ほかを配るなら `FIRST_EFFECTS` に足します（足さなければ、作品には手で写します）。作品の `effects/` は作ったときの写しなので、直しても他の作品には移りません。
- **描画確認と回帰チェック**：書いたら、写しのタイムラインで静止画を描いて目で見ます（下の 6）。既存の作品のエフェクトを直したら、直す前と静止画の SHA を比べて、変わったのが狙ったところだけか確かめます。

## 6. 描く・確かめる（コマンド）

### 基本コマンド（静止画・書き出し・音・プロキシ）

- **作品の中からは中継がいちばん簡単**：`python .mittler/engine.py stills <タイムライン> --at 5,12.5 --out work/stills`（作品のフォルダで実行。引数は下の `python -m mittler` と同じ。`.mittler/env.json` の描く python・ffmpeg のフォルダを使い、Mittler の `pyengine` を `PYTHONPATH` に入れて動かします。終了番号はエンジンのものです）。
- **直接動かすとき**：
  - 作業ディレクトリ（cwd）：`<mittler>/pyengine`
  - Python：その PC の描く python（numpy・opencv・Pillow。`.mittler/env.json` の `render_python`・設定 `mittler.render.python`。分からなければ `python <mittler>/setup/mittler_setup.py --json` の `render_python`）
  - `ffmpeg` が PATH に無い PC は、先に PATH へ足します（`set PATH=<ffmpeg の bin>;%PATH%`）。

```
python -X utf8 -B -m mittler stills <tl.cut.json> --at 5,12.5 --out <フォルダ>              静止画（still_<秒>.png）
python -X utf8 -B -m mittler video  <tl.cut.json> <出力.mp4> --jobs 16 [--from S --to E]   書き出し（PROGRESS を出す。<出力>.cancel で止まる）
python -X utf8 -B -m mittler mix    <tl.cut.json> <出力.wav> [--from S --to E]             音だけ（numpy なしでも動く）
python tools/make_proxy.py <tl.cut.json> <動画.mp4> [--no-timeline]                        再生用の WebM（--no-timeline でなければ preview.proxy も書く）
```

- **コマ時刻と再現性**：書き出しのコマの時刻は並列数・`--from` によらず `n / fps`（通しのコマ番号）です。そのため、止めた 1 コマ・静止画・並列 1・並列 16 は同じ絵になります（映像クリップも、どこから開いても「素材を頭から順に読んだ並び」の同じコマが出ます）。同じパッケージの版の python なら PC が違っても同じ絵になります（`setup/requirements-engine.txt` の版で確認済み）。
- **異常終了・制約・長時間処理**：
  - 書き出しが失敗・中止しても、途中の区間ファイル（`output/_tmp/`）は残りません。
  - 幅か高さが奇数の作品は、描く前に理由を出して止まります。
  - 音・セリフのクリップが何百個あっても音を混ぜられます（長いフィルタはファイルで渡します）。
  - 長い書き出し・確認は黙って待ちません（進み具合の `PROGRESS` 行を確認します。サブエージェントに任せるなら、指示書には要約でなく全部の情報を渡します）。

### 計測・プレビュー・ドラフト・読み込み・先読み

- **描くのが重いときの計測**（2026-10-30）：`/api/frame?t=<秒>&prof=1`（描画サーバーなら `/frame?t=<秒>&prof=1`）。キャッシュを使わずに描き、応答ヘッダ `X-Mittler-Prof` に重いもの上位 5 件（`<エフェクト>@<クリップの id>:ms`・`video`＝映像の取り出し・`subtitle`＝ASS の字幕・`jpeg`）、全部の内訳（段ごと・エフェクトのクリップ 1 本ごと）はサーバーのログに 1 行の JSON（`[engine] {"prof": …}`）で出ます。`prof` を付けなければ何も測りません（絵も速さも今までと同じ）。
- **プレビューの縮小**（2026-10-30）：`/api/frame?…&scale=0.5`（既定 1）。書き出しのドラフトの大きさと同じく、等倍で描いてから縮めます（エフェクトの params は画素の大きさのまま）。編集画面は既定 `0.5`（プレビューの下の「プレビュー 等倍／1/2／1/4」）。止めたときの `current_frame.jpg` もその大きさになります。PNG で保存（`/api/still`）と書き出しは常に等倍です。
- **ドラフト品質**（2026-10-30、機能追加案01）：`/api/frame?…&draft=1`（描画サーバーなら `/frame?…&draft=1`）と書き出しの `--draft` では `ctx.draft` が `True` になり、対応したエフェクト（`ctx.draft` を読むもの。`META` の `'draft': True` が印）だけが軽く描きます。読まないエフェクトと、`draft` なしの絵（PNG で保存・本番の書き出し・ふつうのプレビュー）は今までと 1 ビットも同じです。キャッシュ・先読みは `draft` ごとの別枠で、止めたときの `current_frame.jpg` にはドラフトの絵を入れません。編集画面はまだ `draft` を付けません（再生・シークの間だけ付ける想定）。静止画は `mittler stills … --draft` のときだけです。エフェクトの対応方法は `docs/エフェクトの書き方.md` の「ドラフト品質」を参照してください。
- **読み込み**（2026-10-30）：人のマスクの PNG は `helpers.read_gray` がデコードしたものを覚えます（`settings.cache.mask_mb`、既定 512）。映像を GPU で読むのは `settings.decode.hwaccel: "cuda"` か `mittler … --hwaccel cuda` です（既定オフ。絵は CPU と同じ。偽マリアの小さい素材では GPU の準備の分かえって遅いです）。形式は `docs/タイムライン形式.md` を参照してください。
- **先読み**（2026-10-30）：描画サーバーは JPEG の 1 コマに答えたあと、0.2 秒ほかの頼みが来なければ、その先の 1 秒ぶんを同じ画質・縮小で描いてキャッシュ（120 枚）に入れます。新しい頼みが来たら、エフェクトの区切りでやめて本線に渡します（待つのは長いエフェクト 1 本ぶんまで。偽マリアで平均 0.17 秒）。`prof=1`・PNG で保存では先読みしません。`mittler serve … --ahead 0` で切れます。キャッシュはタイムラインか `effects/` の下の `.py` が変わると捨てます。

### マスター書き出し（2026-10-30、機能追加案03 v2）

編集画面の「マスター」、または次のコマンドで実行します：

```
python -X utf8 -B -m mittler master <tl> <出力.mp4> [--from S --to E] [--jobs N] [--force] [--check] [--fresh]
```

- **処理の流れ**：
  0. 書き出し前チェック：作品のエフェクトのうち `META` に `'scale_aware': True` の無いものを名指しで止めます（`--check` はここまで）。
  1. ① 映像素材を Real-ESRGAN で長辺 3840 にアップスケール（作品の `work/master/upscale/`、キャッシュ）。
  2. ② RIFE で 60fps に補間（`work/master/interp/`、キャッシュ）。
  3. ③ キャンバス 2 倍・60fps で全部を描画（`ctx.scale`＝2、素材はキャッシュに読み替え。タイムラインは書き換えない。区間に分けて並列、並列数は自動）。
  4. ④ area（既定。`--down lanczos` も可）で 1080 に縮めて `settings.export` の設定でエンコード、音はいつもの mix／loudnorm。
  5. ⑤ ③ の中間ファイルを削除（キャッシュは上限 GB まで残す）。
- **進捗・停止・エフェクト対応**：進み具合は `PHASE`（`check`・`upscale i n`・`interp i n`・`render`）と `PROGRESS`、止めるのは `<出力>.cancel`（編集画面の「止める」）、止まった理由は `MASTER_STOP <JSON>` の行に出ます。エフェクトの対応方法は `docs/エフェクトの書き方.md` の「マスター書き出し（ctx.scale）」を参照してください。いつもの書き出し（`mittler video`）と静止画・プレビューは今までと 1 ビットも同じです。
- **所要時間とツール**：
  - 通常の書き出しの約 10 倍の時間がかかります。Real-ESRGAN・RIFE の exe の場所などの設定はインストールガイドの 12 を参照してください（無い PC でも、映像素材が無い作品なら書き出せます。要るのに無ければ理由つきで止まります）。
  - 本物の道具で確かめた版：Real-ESRGAN ncnn-vulkan 20220424（xinntao/Real-ESRGAN の v0.2.5.0）と rife-ncnn-vulkan 20221029。入手先・版・SHA-256・置き方はインストールガイドの 12「Real-ESRGAN・RIFE の入れ方」。
  - 目安（RTX 3090）：素材 1 秒（24fps）あたり、アプスケ約 2.5 秒・4K の補間約 8 秒（2026-10-31 の並列化後は、偽マリアの素材で ①② あわせて約 8 秒。前は約 25 秒）、VRAM は RIFE（4K）で約 3.3 GB。道具の入れ替え・別の PC への設置はユーザーの許可が必要です（外のダウンロード）。
- **キャッシュと `--fresh`**：
  - 補間する素材は補間ずみだけを残し（アプスケずみは補間に入れたら捨てる）、補間しない素材はアプスケずみを残します。保存形式は H.264 を RGB のまま（`libx264rgb`・crf 10、名前の終わり `_x264rgb10.mkv`。前の FFV1 の 1/6〜1/10、最後の 1080 の絵で PSNR 56〜62 dB＝見分けられない）。前の形（名前に形の印が無いもの）は使いません（上限の掃除で消えます）。単体の `--cache-fmt ffv1` で可逆にもできます。
  - **キャッシュを捨てて新規で**：マスターの窓の詳細設定のチェック「キャッシュを使わずに作り直す」（既定オフ。`POST /api/export` の `{master: true, fresh: true}`）、単体は `--fresh`。チェックと道具の確かめが通ったあとに、その作品の `work/master` の `upscale`・`interp` の中のファイルと `hashes.json` を捨ててから作ります（ほかの作品・tmp には触りません）。詳細設定の「キャッシュ」の「削除」ボタンはいますぐ `*.mkv` を消すだけです。ユーザーに「キャッシュを捨てて作り直して」と言われたら `--fresh` を使います（自分で `work/master` を消さない）。
- **アップスケールのモデル**：
  - アニメ（`anime`＝`realesr-animevideov3`、x2〜x4 の足りる最小）と実写（`real`＝`realesrgan-x4plus`、x4 で上げてから 3840 に縮める）の 2 種類です。
  - 指定場所：作品はタイムラインの `settings.master.upscale`（マスターの窓の「画質」で選ぶ：標準＝`none`・高画質（アニメ）＝`anime`・高画質（実写）＝`real`。窓から始めた書き出しは窓で選んでいるものを `--upscale` で渡す）、クリップは `upscale`（映像クリップの欄の「マスター画質」。動画化予定のクリップも JSON で指定可能）、単体は `--upscale anime｜real`（作品の設定の代わり。クリップの `upscale` は効く）。どこにも無ければ PC の設定 `esrganModel`（既定アニメ）＝今までと同じです。
  - キャッシュはモデルごとに別名です（同じ素材を別のモデルの 2 つのクリップが使えば両方作り、クリップごとに読み替える＝差し替え表の `'@clips'`）。
  - 実写は写真のような素材の模様（ヒョウ柄・スパンコール・ラメ）を元の形のまま残します（アニメは平らに描き直す）。実写の ① は約 11 倍遅いです（RTX 3090 で 1344×768 の 1 コマ 2.07 秒、VRAM は RIFE と同時で +5.7 GB）。ユーザーの作品で勝手にモデルを変えません（作品のファイルが変わる・①② のやり直しで時間がかかる）。くわしくはインストールガイドの 12「アップスケールのモデル」。
- **アップスケールなし（60fps だけ）**：
  - 作品の `settings.master.upscale` が `"none"`（マスターの窓の「画質：標準」）か単体の `--upscale none` で有効になります。
  - ① はしない（Real-ESRGAN 不要）、② は素材の元の大きさのまま補間、③ はキャンバス 1 倍・60fps、④ の縮小は無し（出力＝タイムラインの大きさ。`--master-scale`・`--master-out`・PC の設定の `scale`・`outHeight` は使わない）。
  - `scale` が 1 なので書き出し前チェックの `scale_aware` は見ません（止めない）。`uses_fi` の注意は出します。補間ずみのキャッシュ名はアプスケしない素材と同じ `<ハッシュ>_60_<形>.mkv`（中身も同じなので 4K のマスターと使い回します）。
  - 「なし」は作品全体の形なのでクリップの `upscale` には書けません（名指しで止まる）。作品が「なし」のとき、クリップの `anime`・`real` は使いません（`MASTER_WARN` に名前を出します）。`MASTER_DONE` の `upscale` は `"none"` です。くわしくはインストールガイドの 12「アップスケールなし（60fps だけ）」。
- **並列化**：
  - すべて自動です（CPU 数と空きメモリから決定。ほかの PC でもそのまま）。
  - ①② は道具の `-j`（PNG の読み書きのスレッド。作者の PC で Real-ESRGAN `2:2:8`・RIFE `8:2:16`）と、素材ごとに重ねます（素材 i の補間と i+1 のアプスケ、補間のエンコードも次の素材と重ねる。同じ道具は 1 本ずつ）。
  - ③ は並列数＝CPU の半分と空きメモリ（1 本 2.5 GB）の小さいほう（作者の PC 12）、区間は範囲を 128 に分けて順に流します（区間数は並列数によらないため、並列数を変えても MP4 は同じ）。手動変更は単体の `--jobs`・`--chunks`・`--threads`（OpenCV、既定は絞らない）・`--esrgan-j`・`--rife-j`、マスターの窓の詳細設定の「同時処理数」（空＝自動）。
  - **並列を 16 より上にしない**（作者の PC で 24 はメモリが足りなくなり、止める（`.cancel`）も 150 秒以上届きませんでした）。
  - 目安（作者の PC、偽マリア 14〜26 秒＝素材 3 本 → 4K・60fps の 720 コマ）：前の版 1416 秒（①② 310・③④ 1104）→ 今の版の表はインストールガイドの 12「マスター書き出しの並列」。③ はエフェクトの計算（4K の光のぼかしなど）で CPU が詰まるため、全プロセス稼働中の速度は並列 4 とほぼ同じで、速くなるのは区間を細かくして最後の待ちを減らした分（1.2 倍前後）です。偽マリア全部の見込みは前の版 4.2〜4.4 時間 → 2.9〜3.5 時間（推測）。それ以上はエフェクトの描き方を変える話になります（絵が変わるためユーザーに聞く）。

### 動画 1 本を高画質にする

作品は不要で、動画単体を高画質化できます：

```
tools\enhance.cmd <動画> [<出力.mp4>] [--upscale anime|real|none]
```

- 実体は `python -X utf8 -m mittler enhance …`（`pyengine/mittler/enhance.py`）です。
- オプションはアップスケールの方法だけ（既定 `anime`）です。`anime`・`real` は出力＝マスターと同じ大きさ（短い辺 1080・縦長もそのまま）、キャンバス＝その 2 倍で ①② → ④ area で縮めます（③ 描くは無し）。`none` は元の大きさのまま ② だけです。
- 処理は `master.py` の `tools_pass`・`missing_tools` と `__main__` の `rgb_encode_cmd`・`vcodec` をそのまま使います（同じ動画 1 本だけを置いた作品のマスター書き出し（区間 1）と映像のストリームまで同じ）。
- 音は入力の音をコピーします（できない形は AAC 256k）。キャッシュは出力のフォルダの `_enhance_<番号>/` に作って終わったら消します（隠しの `--work <フォルダ>` で残せます）。
- 道具の場所は環境変数 `MITTLER_ESRGAN`・`MITTLER_RIFE`（VS Code の設定は読みません）。止まり方・進み具合の行はマスターと同じです（`MASTER_STOP`・`PHASE`・`PROGRESS`・`MASTER_DONE`）。くわしくはインストールガイドの 12「動画1本を高画質にする」。

## 7. 動作確認（smoke test）

smoke test には 3 つの実行形態があります。いずれも試しの作品で流し、ユーザーの作品では流しません。

### 実行形態と前提

1. **サーバーもブラウザも不要なもの**（コミットの前に流す）：
   - `python -X utf8 tools\smoke_text.py`（見えない字）・`python -X utf8 tools\smoke_docs.py`（文書）
   - `<描画の python> -X utf8 tools\smoke_same.py`（同じ計算）・`tools\smoke_setup.py`（初期設定の確かめ）・`tools\smoke_3d.py`（3D。GPU・Blender のある PC では `--require-gl --blender <exe>`）
2. **自分で試しの作品を作り、サーバーを立てて止めるもの**：
   - ブラウザなし：`<描画の python> -X utf8 tools\smoke_bugs.py`・`tools\smoke_package.py`
   - ブラウザあり：`<Playwright の python> -X utf8 tools\smoke_ui.py --render-python <描画の python>`・`tools\smoke_bugs_ui.py --render-python <描画の python>`
3. **立ててあるサーバーの URL を渡すもの**（残りの smoke）：
   - 実行：`<Playwright の python> -X utf8 tools\smoke_*.py <URL> --timeline <試しの作品のタイムライン>`
   - 試しの作品の作成：`tools\mittler.cmd node tools\new_project.js <一時フォルダ>\<名前> --title 試し`（素材は ffmpeg の lavfi で作れる）
   - サーバーの起動：`tools\mittler.cmd serve <試しの作品>\<名前>.cut.json --port <N> --render-python <描画の python>`（環境変数 `MITTLER_NO_REVEAL=1` でエクスプローラーを開かない）
   - URL はサーバーの 1 行目、停止は `POST /api/quit`（ヘッダ `X-Mittler-Token`）です。
   - `smoke_export.py` は名前が `*.test.cut.json` のタイムラインでないと動きません（試しの作品でも写しを作ります）。

- **画面の言葉**：smoke は日本語の画面の言葉で確かめます。URL を渡すものはサーバーを `--lang ja` で立て、URL の `?token=` の前に `lang=ja&` を入れて渡します（`…/editor/?lang=ja&token=…`）。試しの作品も `new_project.js … --lang ja` で作ります（トラックの名前が日本語の作品）。自分でサーバーを立てるもの（`smoke_ui`・`smoke_bugs`・`smoke_bugs_ui`）は自分で `--lang ja`・`&lang=ja` を付けます。英語（既定）の画面は `tools\smoke_i18n.py` が確かめます。
- **Python 環境とブラウザの制約**：描画の python は numpy・opencv・Pillow の入ったもの（`setup/requirements-engine.txt`）、Playwright の python は Playwright（Chromium）の入った venv です。**ブラウザで開くのは localhost だけ**にします（外のサイトを開かない）。
- **ほかの PC（Remote-SSH の先など）でサーバーを動かすとき**：その PC で `tools\mittler.cmd serve …` を動かし、`ssh -L <N>:127.0.0.1:<N> <その PC>` で転送して `http://127.0.0.1:<N>/…` を開きます。タイムラインのファイルを直接読む smoke はこの形では使えません（対応しているのは `smoke_export.py` の `--remote-project` のみ）。
- **前から落ちる項目**（smoke か試しの作品の前提の問題。アプリの失敗ではなく、直すかは未定）：
  - `smoke_snap` の「▾ で拍を外すと拍に吸いつかない」（原因は未特定）
  - `smoke_presets` の「一覧で『入っている』になる」（写すところまでは通るが、そのあと時間切れ）
  - `smoke_warp` の「エンジンの絵＝動画の N コマ目」など 3〜4 項目（試しの動画が「動いている人」でないため。開いた直後に重なると、ほかの項目がときどき落ちる）
  - `smoke_state` は重いときに 1 回だけ落ち、流し直すと通ることがある

### テスト後の後片付けとドライラン

- **タイムラインの復元**：どれも最後に取り消しでタイムラインを最初に戻し、戻らなければファイルを書き戻します。ブラウザは localhost のみ開きます（外のサイトを開かない）。
- **既存プロセスの保護**：ユーザーが開いているかもしれない作品・サーバー・ssh には触りません（自分が起動したものだけ止める）。テスト後は自分のプロセスを止め、残したものを報告します。
- **残った描画サーバー・ジョブ係の停止**：テストのサーバーを強制終了すると、描画サーバー（`mittler serve`、ポート 47900〜47989）が残ります。テスト後はサーバーを動かした PC で `netstat -an | findstr LISTENING | findstr 127.0.0.1:479` を確認し、各ポートの `/info` の `name` を見て、**自分のテスト用の作品のものだけ** `/quit` します。テストで動いたジョブ係（`tools/jobs.py`）も止めます。
- **外部生成を動かさない検証**：H3・Codex を本当に動かさずに確かめるときは、サーバーを `MITTLER_MYDRIVE`・`MITTLER_H3_ROOT` を偽のフォルダに向けて起動し、`--dry` で動かします（H3 の結果まで通すなら `smoke_plan.py` の模擬の H3）。エクスプローラーを開かないよう `MITTLER_NO_REVEAL=1` を付けます。

## 7.5 生成のジョブ

- **ジョブの流れ**：編集画面の「生成」「動画化」→ サーバーが `work/jobs/job_*.json` を書く → ジョブ係 `tools/jobs.py`（この PC で動く。生成は常にローカル）が実行 → できたら編集画面がテイクに入れます（タイムラインを書くのは編集画面だけで、ジョブ係はタイムラインを書きません）。
- **画像生成エンジンとアダプタ**：
  - **Codex**：`tools/codex_jobs.py` → `tools/gen/codex_image.py`（同時 1 件、参照 5 枚まで、作品ごとの Codex セッション）
  - **OpenAI**：`tools/openai_image_jobs.py` → `tools/gen/openai_image.py`（OpenAI の Image API。参照 16 枚まで、モデル・品質を選べる、鍵は資格情報マネージャーの `ps:OPENAI_API_KEY`。2026-11-15〜）
  - **Nano Banana**：`tools/gemini_image_jobs.py` → `tools/gen/gemini_image.py`（Gemini の generateContent。参照 14 枚まで、モデル・解像度を選べる、鍵は Gemini TTS と同じ `ps:GEMINI_API_KEY`。2026-11-19〜）
- **エンジン・モデル・品質の優先順位**：
  - エンジン：絵の欄の `engine`（`codex`・`openai`・`nanobanana`。API の `--engine` もここ）→ 作品の `settings.image_engine`（作品の既定）→ PC の設定 `mittler.image.engine` → Codex。
  - OpenAI のモデル・品質：絵の欄の `model`・`quality` → 設定 `mittler.openai.imageModel`・`imageQuality` → `gpt-image-2.5-sunburst`・`high`。
  - Nano Banana のモデル・解像度：絵の欄の `model`・`quality`（解像度）→ 設定 `mittler.gemini.imageModel`・`imageSize` → `gemini-3-pro-image`（Nano Banana Pro）・`2K`。
  - Codex CLI の場所・モデル：PC の設定 `mittler.codex.path`・`mittler.codex.model`（インストールガイドの 12）。
- **動画生成エンジンと対応表**：
  - 動画は H3 のアダプタ `tools/h3_jobs.py`（H3 のキュー）を使います。
  - どのエンジンをどのアダプタで動かすかは `tools/engines.json` の 1 か所で管理しています（サーバーもジョブ係もそこから引きます。エンジンの足し方は `docs/H3受け渡し契約.md` の 13）。
  - H3 との受け渡し（素材フォルダ・inbox の依頼の YAML・outbox の結果・上書きできるキーと既定値・止めたとき）の正本は **`docs/H3受け渡し契約.md`** です。H3 の決まり（17k+5 コマ・声の長さ・参照の数・プロンプトの形・既定値）を持つのはアダプタ `tools/h3_jobs.py` の 1 か所だけです（サーバーはジョブを作るときに `h3_jobs.py build` を呼びます）。
- **状態・ログ・停止・排他制御**：状態は `GET /api/jobs`、ログは `work/jobs/runner.log`、停止は `POST /api/jobs/<id>/cancel` です。ジョブ係は作品ごとに 1 つだけ動きます（`work/jobs/runner.lock` に OS の鍵をかけ、同時に起動しても進むのは 1 つ）。何も無ければ 15 分で自動終了します。

## 7.52 H3 の動画のプロンプト（動画化）

プロンプトを書く前に、`docs/技術集/07_動画生成と口パク.md` と `docs/技術集/07b_口パク_ref2va_話者の指定と成功例.md`（口パクの話者の指定・失敗した形・成功例の全文）も読んでください。

### ふつうの動画化（fl2va）の書き方

基本は開始フレームだけにして、ミリ秒単位のポーズと演出の指示を細かく書き込みます。

0. **1 本は 2〜6 秒に区切る**
   - 長い動画は生成時間が跳ね上がるため、基本は 6 秒以内にします。
   - 6 秒をこえるカットは、動画化予定のクリップを 2〜6 秒ずつに分けて別々に出します（続けてつなぐなら、前のテイクの最後のコマを次のクリップの開始フレームにします）。
   - 6 秒をこえるクリップで出すと、ジョブの知らせ（`warnings`）に注意が出ます（止めはしません。長くしてよいのはユーザーに頼まれたときだけです）。
1. **基本は開始フレーム（`start_frame`）だけにする**
   - `end_frame` は空のまま出します。終わりの絵を渡すのは、ユーザーに頼まれたとき・次のカットへ絵でぴったりつなぐ（マッチカットなど）と決めたときだけです（終わりの絵があると、そこへ合わせるために途中の動きが小さく・ぎこちなくなりやすいため、動きはプロンプトで決めます）。
2. **ポーズと演出を、ミリ秒の時刻で細かく書く**
   - クリップの長さ（`video.seconds`）を `0.000` から終わりまですき間なく区切ります（1 つの区切りは 200〜800 ms が目安。速い動き・瞬き・手の向きが変わる所は細かく）。
   - 区切りごとに、体の向きと重心・頭の角度・目線・まばたき・口・眉・手と指（どちらの手・どの指・何をつまむか）・息・髪と服の揺れ・小物の動き・カメラ・光と効果（ちらつき・粒・反射）を、何がどれだけ動くかで書きます（`"a few millimeters"`・`"a few centimeters"`・`"eases to a stop"`）。
   - 時刻は生成する動画の頭からの秒（`video.seconds` の長さ。曲の秒ではない）で書きます。
3. **構成の形（英語で書く。作者の作品で通ったもの）**
   - ① **開始フレームの説明**：ショット（寄り・引き・アングル）・場所・人物（見分けられる特徴：髪型・髪飾り・服・年齢と体つき）・目線・光源。「`continuing the first frame exactly`」。
   - ② **時系列の演技**：`Acting, beat by beat (the shot is N.NNN seconds, …):` に続けて、`0.000-0.350s: …` の行を時刻の順に並べます。
   - ③ **動かないものの明言**：背景・家具・小物の形と数・人と手の数を言い切ります（`"stay perfectly still and keep exactly their shapes"`・`"only this one person"`・`"only one hand"`）。
   - ④ **カメラ**：push-in・固定・`no pan, no cut`。
   - ⑤ **光**：向きと色は first frame のまま。
   - ⑥ **画風と外見の維持**：画風と顔・目の色・髪・服を first frame のまま（`no 3D rendering, no photorealism` など）。
   - ⑦ **禁止事項**：`no stutter, no freeze, no morphing`・`no text, captions, logos or watermarks`・涙・余計な人や手など、そのカットで崩れやすいもの。
   - 例（ミリ秒で区切った ② の一部）：
     - `0.000-0.400s: she stands perfectly still, lips slightly parted, eyes wide, staring at the white screen.`
     - `0.400-1.050s: she takes a slow breath in; her shoulders rise about one centimeter; the reflections of the screen in her eyes tremble.`
     - `1.050-1.300s: she blinks once, slowly.`
     - `1.300-2.100s: her eyebrows lift gently and her lips close into the faintest smile; a loose lock of hair at her cheek stirs.`
4. **崩れたときの修正**
   - 崩れた所を名指しで足します（人物の見た目がずれる → 年齢・体つき・手の形を言い切る、背景が変わる → その物の位置と形を言い切る）。同じ文のまま種だけ変えて何本も出しません。

### 守ること（しゃべりは fl2va・口パクの ref2va は歌だけ）

> **H3 の動画（動画化）のプロンプトを書く前に、必ず以下を読んでください**（これを読まずに書いて口パクの失敗が続いたことがあります）。

- **しゃべり（アニメのせりふ）は ref2va を使わない**：fl2va（声を渡さない）で絵を先に作り、セリフはあとで口に合わせます（アフレコ）。**ref2va は歌だけ**に使います。
- **ref2va は 1 本の声＝1 人**：歌う人を `(S1)` として `subject_definitions` に見た目と位置で書き、`<Audio 1>: fully_copy - … (S1) sings a song.`、ほかの人は `(S2) does not sing.` と「唇とあごを動かさない」を明記します。1 本の声に 2 人のせりふを混ぜると話者も時刻も効かない（失敗例あり）ため、掛け合いは 1 人ずつの区間に分けて別々に作ります。
- **約 0.4 秒以上の無音を避ける**：声の途中に約 0.4 秒以上の無音があると、音を写さずに作り直されやすくなります。無音は声のほうで詰めるか、そこで区間を分けます。
- **口合わせ重視のカットは演技を控えめに**：演技を大きく書くと声の写りが落ちます。
- **時刻軸と顔の対策**：プロンプトの時刻は**生成の時間軸**（前に 0.5 秒の無音が足される：`曲の秒 − audio_start ＋ 0.5`）です。顔の対策（`ref_image_size max`・顔の参照・顔の言葉・Look の行・`beta`・25 step）は成功例どおりにします。
- **Mittler から出すときの仕様（`tools/h3_jobs.py`、`docs/H3受け渡し契約.md`）**：プロンプトが 6 節の形（`subject_definitions:` …）なら、書いたとおりに送ります（前置き・キャラの外見・画風を足さない）。ref2va は `ref_image_size: max`・`scheduler: beta`・`steps: 25` を最初から入れます。変える場合はクリップの `video.h3`（例 `{"steps": 20, "seed": 123}`。使える名前は `tools/h3_jobs.py` の `H3_KEYS`）で指定します。顔の参照は `@import char(…)` の画像が `ref_images` になります。

## 7.53 Claude Code から頼む（tools/mittler_api.py）

### 生成ジョブと基本の使い方

- **ジョブファイルを手書きしない**：Claude Code（編集画面の外）から生成を頼むときは `tools/mittler_api.py` を使います（2026-10-26）。`work/jobs/job_*.json` を手で書かないでください（参照の展開・出力の名前・シードはサーバーの `createVideoJob`、H3 の 17k+5 コマ・`H3_tasks` の場所などの決まりはアダプタ `tools/h3_jobs.py` が組み立てます）。
- **前提と接続先**：編集画面（その作品の `*.cut.json`）が開いている必要があります。サーバーは起動すると `.mittler/server.json`（ポート・トークン。git に入らない）を書き、`mittler_api.py` がそれで頼みます。無い・つながらないときは、ユーザーに編集画面を開いて（開いていればウィンドウの再読み込み）もらいます。
- **中継コマンド**：作品のフォルダからは中継 `python .mittler/api.py . <コマンド>` を使います（中身は Mittler の `tools/mittler_api.py`、引数も同じ。下の `python <mittler>/tools/mittler_api.py <作品>` と同じです）。
- **動画・画像の生成依頼**：
  - 先にプロンプトなどをタイムラインのファイルに書き（`plan` の `video.prompt`・`engine`、`start_frame.src` など。編集画面が読み直します）、`python <mittler>/tools/mittler_api.py <作品> video plan_01 plan_02` を実行します（`--all`＝プロンプトがあってテイクも動いているジョブも無い予定を全部、`--dry`＝H3 に出さずに中身だけ確かめる）。絵は `image <クリップ> start_frame|end_frame`、状態は `jobs`・`status` です。
  - 下書き：`video … --draft [--steps 10]`（編集画面の「動画化予定の下書き」と同じ）。シードはクリップの `video.seed`、無ければサーバーが作品とクリップの `id` から毎回同じ値を決めるため、下書きと本番は同じシードになります。テイクには `draft`・`steps`・`seed` が入ります。
  - H3 は時間と計算機を使うため、出す前に何本・どのクリップかをユーザーに伝えてから実行します（頼まれた分だけ。0 の計画の使用量の OK の範囲ならその中で）。
- **テイクの反映・採用・同名上書き**：
  - できた動画・絵をテイクに入れるのは編集画面です。`mittler_api.py` で頼んだものも、ジョブのファイル（`work/jobs/job_*.json`）が変わるとサーバーが知らせ（変更通知 `jobs`）、開いている編集画面が見に行ってテイクに入れます（2026-10-31〜。前は開き直すまで入らなかった）。編集画面を閉じていたら次に開いたときに入ります。
  - 採用（映像トラックに置く）はユーザーが行うか、頼まれたら Claude が `adopt <予定> [<テイク>]`・`adopt-all [--latest]` で実行します（編集画面の「採用」と同じ。下の表）。
  - 絵・動画のファイルを**同じ名前で上書き**したときも、編集画面（サムネ・テイクの絵。変更通知 `media`）と描画サーバー（使うファイルの更新時刻）が読み直します。描画サーバーが見ているのは、映像・動画化予定のクリップが使うファイルと、エフェクト・字幕のクリップの `params`・`style` が指すファイル（`sprite` の `img`＝フキダシ・描き文字、書体など）です。エフェクトのコードが自分で決めた名前で読むファイル（パラメータに出てこないもの）は見ていないため、タイムラインを保存し直すか「読み直す」を実行します。それでも出ないときは、ユーザーに上のバーの「読み直す」（画面の読み直し）を押してもらいます。

| カットの段 | `cut-first`・`cut-lane cuts\|notes`・`cut-split <秒> [--label L]`・`cut-join <L> prev\|next`・`cut-remove <L>`・`cut-rename <L> <新>`・`cut-edge <L> start\|end <秒>`・`cut-align [<L>…]`・`cut-from-clip <クリップ>`・`cuts-on-adopt on\|off` |
| 解析 | `analyze <クリップ> <種類> [--wait]`・`analyses [--wait]`（タイムラインに入れるのは編集画面） |
| ステムを置く（Suno の audio-stems の WAV など） | `stems-place <音のクリップ> <WAV>…`（パートごとにミュートした音のトラック。名前はファイルの名前） |
| 部品の置き場・キャラのプリセット・Blender のためた絵・ためたコマの絵 | `effects`・`effect-add <名前>`・`presets`・`preset-add <id> [--overwrite]`・`blender-clear <クリップ>`・`frame-cache [clear]`（書き出し・プレビュー・裏の係で描いてためたコマ。直した区間だけ描き直すので、ふつうは消さなくてよい。**書き出しもためた絵を使う**ので、エフェクトが鍵に入らないファイル（決まった場所の解析結果など）を作り直したら消すか、`export --no-cache`。エフェクトの書き方の「ためた絵」） |
| 新しい作品（「＋ 新規」） | `new-project <親のフォルダ> <名前> [--title T] [--width W --height H --fps F --duration D] [--lang ja] [--no-git] [--no-open]` |
| **画面の見える操作**（作品は変えない） | `ui play`・`ui pause`・`ui seek <秒>`・`ui step <コマ>`・`ui select <クリップ>… [--seek]`・`ui select --none`・`ui select-track <トラック>`・`ui pane clip\|color\|meta`・`ui zoom <px/秒>`・`ui fit`・`ui scroll <秒>`・`ui lang en\|ja`・`ui open-export`・`ui open-master`・`ui close-export`・`ui reload`・`ui undo`・`ui redo`・`ui follow on\|off`・`ui state` |

- **選択とオートの挙動**：`ui select` すると編集画面の `.mittler/state.json` とフックにもすぐ反映されます。`ui seek`・`ui select` の直後（3 秒）は、オートで再生位置を飛ばしません（頼んだ所が勝ちます）。
- **ファイル直接編集で済むもの**：クリップの値・トラックの追加と並び・ミュート・メタデータの文字・色の値・動画の長さと大きさは、従来どおりタイムラインファイルを直接編集します（API の口はありません。計算が要るものだけを API 化しています）。
- **人がやるもの（API にしない）**：Suno の採用（ダウンロード用のクレジットの OK）、H3 の動画の生成（Colab の許可ボタン）、書き込み（人が描いて AI に渡すもの）、試聴、エクスプローラー・VS Code でファイルを開く、OS のフォルダ選び、「Mittler: 初期設定」で入れるもの（入れることの OK）。
- **API で頼めても、決まりは変わらない**：生成・外に送ること（Codex・H3・Gemini TTS・Suno）は 0 の計画の使用量の OK の範囲内（範囲の外・計画の前はユーザーに一言）、作業のたびにコミット（プッシュは頼まれたときだけ。4.5）、開いている作品を直接直す原則を守ります。

## 7.54 クリップの解析

- **実行方法**：人は**クリップを右クリック**、Claude は `python <mittler>/tools/mittler_api.py <作品> analyze <クリップ> <種類>`（`analyses [--wait]` で一覧・終わるまで待つ）を使います。

| クリップ | 種類 | 結果 | タイムラインへ |
|---|---|---|---|
| 音 | `beats`（librosa） | `beats.json`（`[秒, 小節の頭か]`・テンポ） | メタデータ `beats`「ビート（…）」（スナップにも効く） |
| 音・セリフ | `transcribe`（faster-whisper large-v3） | `transcript.json`（区切り・単語の時刻） | メタデータ `lyrics`（音）／`dialogue`（セリフ）「文字起こし（…）」 |
| 音 | `stems`（demucs htdemucs） | `vocals.wav`・`no_vocals.wav` | ミュートの音のトラック 2 本 |
| 映像・画像 | `pose`（YOLO11 pose） | `pose.json`（コマごと、人ごとに box・17 点、座標 0〜1） | 入れない（知らせだけ） |
| 映像・画像 | `mask`（YOLO11 seg） | `mask.mp4`（白＝人）／`mask.png` | 入れない |
| 画像 | `cutout`（rembg） | `cutout.png`（透明つき） | 入れない（画像タブから置ける） |

- **対象区間と時刻**：解析するのはクリップが使っている区間だけです（音・セリフは `in`〜`in+dur`、映像は速さ・音ハメの点も見る）。結果の秒は区間の頭からで、タイムラインに入れるとき `start` を足します。
- **仕組みと保存先**：サーバーが同じ PC の解析用の python で `pyengine/mittler/analyze.py` を動かし、作品の `<素材の根>/assets/analysis/<クリップ>_<種類>_<日時>/`（`result.json` と成果物）に回収します（1 つずつ順次実行）。状態は `.mittler/analyze.json` と `GET /api/analyze` で確認できます。
- **タイムラインへの反映**：タイムラインに入れるのは編集画面（`analyze.js`。開いていなければ次に開いたとき）です。入れたものは `Ctrl+Z` で戻せます。ポーズ・マスクはエフェクトや Claude が読む素材になります。
- **解析用の Python 環境**：PC の設定 `mittler.analysis.python`（作品ごとなら `settings.analysis_python`）で決めます（既定の場所と入れ方はインストールガイドの 12 と 9）。解析用の python が無い PC では動かないため、ある PC に Remote-SSH で接続して開きます。編集画面を閉じる・サーバーを止めると動いている解析も止まります（結果は入らないため、もう一度頼みます）。

## 7.55 映像の速さ・音ハメ

- **データ形式**：映像クリップの `speed`（一定）または `warp`（点 `{points, smooth, auto…}` または表のファイル）を使います。形と計算は `docs/タイムライン形式.md` の「映像クリップの時間の付け替え」を参照してください。
- **自動の音ハメ**：編集画面の「音ハメ（自動）」（ビートのメタデータが必要）、Claude からは `python .mittler/api.py . onbeat <映像クリップ> [--set 名前=値]…`（ボタンと同じ頼み・同じ入れ方。7.53）を使います。
- **手で計算するとき**：描画サーバーの `GET /warp?q=<JSON>`、またはその PC の python で `from mittler.onbeat import auto; auto(作品のフォルダ, root, q)`（`q` の中身は `pyengine/mittler/onbeat.py` の頭）を実行し、返った `points`・`smooth` を `warp` に入れます。
- **手動調整と動作確認**：拍の位置を手で直すなら `warp.points` を直します（クリップの頭からの秒・動画の秒。戻らないように両方とも増えていく並びにする）。動作確認は `tools/smoke_warp.py`（試し用の作品に動いている人の動画 1 本とビートが必要）です。

## 7.56 Suno の曲（2026-10-30、機能追加案02 v2）

- **正本と前提**：**手順と形の正本は `docs/Suno受け渡し契約.md` の「Mittler 側の受け渡し」**です。Suno の曲を作る・採用するときは、まずこれを読んでください。
- **Suno MCP の確認**：Suno を呼ぶのは Claude Code（AI。Suno MCP `mcp__suno__*`）だけで、Mittler（サーバー・編集画面）は Suno を呼びません。**そのためエージェントに Suno の MCP がつながっていないと曲は作れません**。ユーザーが Suno で曲を作りたいと言ったら、計画の段階で自分の道具に Suno があるかを確かめ、無ければ作り始める前に導入を提案します（手順と代わりの方法は `docs/表現の一覧.md` の 3.5 の頭）。AI は `tools/mittler_api.py` の `music-take` で納品し、テイクに入れるのは編集画面です。

### プロンプトの書き方

曲のイメージをシンプルに書けば生成できます。タグの羅列より自然な文のほうが伝わり、ボーカルありのときはボーカルの明瞭さを優先するように書きます。

- **自然な文でシンプルに書く**（`description`・`style` のどちらも）：昔の Suno のようにタグ（`j-pop, female vocal, 128bpm, emotional, …`）を並べるより、どんな場面のどんな曲か・聞いた人がどう感じるか・音の手ざわり・展開を 2〜4 文の文章で書くほうが伝わります。盛り込みすぎず、言いたいことを絞ります。
  - 例：`A bright, bittersweet J-pop song for the end of a summer day by the sea. A clear, warm female voice sings close to the listener over clean electric guitar and soft synths; the chorus opens up and lifts.`
- **ボーカルありの曲は歌の明瞭さを優先する**：歌声がはっきり前に出て言葉が聞き取れるよう指定します（例：`The lead vocal is clear and upfront, every word easy to understand; the instruments leave room for the voice.`）。リリック演出（歌詞の時刻・字幕）も歌がはっきりしているほど合います。声を埋もれさせる指示（厚い音の壁・強いリバーブ・歪んだ声）は頼まれたときだけにします。
- **歌詞とインストの扱い**：歌詞（`music.lyrics`）は別の欄で、プロンプトに歌詞を混ぜません。インストは `instrumental: true` と曲のイメージの文だけにします。

### 生成・納品・採用で守ること

- **プロンプト確認が先**：**プロンプトは先にクリップ（音のクリップの `music`）に書いて、ユーザーに確かめてから**生成します（生成のクレジットを使用。30 秒・1 曲で 5 ほど）。0 の計画で曲の生成の回数に OK をもらっていれば、その範囲内で進めます。
- **1 回の生成本数（2 本生成の仕様）**：望ましいのは 1 回の生成で 1 本ですが、**今（2026-11-15 に定義を確かめた）の Suno MCP の `audio-create` には `clip_count` が無く、suno.com のサインインでは 1 回で必ず 2 本できます（2 本ぶんのクレジット。1 本だけは頼めない）**。
  - 1 回の生成＝2 本として使用量を数えてユーザーに伝え、1 曲のために何回も呼びません。
  - 呼ぶ前に道具の定義を確認し、もし `clip_count` を受け付ける定義に戻っていたら **`clip_count: 1` を必ず渡します**。
  - **2 本とも納品して、ユーザーが聞き比べる候補にします**。
- **サイドカーの `create_args`**：サイドカーには **`create_args`（`audio-create` に渡した引数そのまま）を必ず入れます**。`music-take` は、`create_args` が無い・`clip_count` が 1 でない・同じ生成の 2 本目（同じ `created`・同じ `create_args`）のとき、結果の `warnings` に注意を出します（受け取りは断らない＝もう作ってしまったもの）。
- **歌詞つきの曲**：クリップの `music.lyrics` に歌詞を書けば Custom（`lyrics`・`style`・`title`。`description` は送らない）で作れます。インストは `instrumental: true` です。
- **歌詞の単語ごとの時刻（`audio-lyrics-alignment`、無料）**：歌のある曲は生成後に取得し（`processing` なら少し待って呼び直す）、返り値そのままをサイドカーの `lyrics_alignment` に入れて納品します。採用時に編集画面が kind `lyrics` のメタデータ「歌詞の時刻（Suno・…）」に行ごとに入れます（`words` に単語の時刻、置けなかった単語＝`success: false` は印、`from_music`・`from_suno`。入れ直すと置きかわる）。リリックの演出（字幕・動く文字）はこれを使います（`docs/表現の一覧.md` の 3.5・5）。インスト曲は何も入りません。
- **生成時はファイルを取らない**：ダウンロード用のクレジットを使わないため、テイクには suno.com の URL・id・プロンプトの全文・`create_args`・解析（`audio-analysis` は無料）・歌詞の時刻だけを積みます。試聴はユーザーが「suno.com で聞く」で行います。
- **採用とダウンロード**：ファイルを取るのは、ユーザーが編集画面で「採用」→ クレジットに OK した（`music.adopt`＝採用待ち）ときだけです。フックが「【🎵 採用待ちの曲…】」を添えるか、`mittler_api.py <作品> music --pending` で確認できます。`audio-download`（**wav**）→ URL は **1 時間で切れる**ためすぐ取得 → `assets/music/<クリップ>_t<n>.wav` に保存 → `mittler_api.py <作品> music-take <クリップ> --take t<n> --src …` で納品します。
- **ブラウザ版で作った既存曲**：Suno の解析が `not_found` になります。ファイルは手で置き（従来どおり）、拍は解析で取ります。
- **ステム（歌・伴奏・楽器ごと）**：Suno の MCP の `audio-stems-create`（`two` 10 クレジット・`twelve` 50 クレジット。先にユーザーの OK）→ `audio-stems-retrieve` の WAV を `assets/music/<クリップ>_t<n>_stems/` に保存 → `mittler_api.py <作品> stems-place <音のクリップ> <WAV>…`（ミュートした音のトラックに配置）。Suno の MCP が無ければ解析の `stems`（demucs）を使います。くわしくは `docs/Suno受け渡し契約.md` の「納品」の 5 を参照してください。

## 7.7 3D の場面（2026-11-13、3D 強化）

3D 表現を強化するため、GPU の 3D（moderngl）と Blender の 3D を用意しています。くわしくは `docs/エフェクトの書き方.md` の「3D のエフェクト」、`docs/タイムライン形式.md` の「Blender の 3D のクリップ」、導入と GPU の注意は `docs/インストールガイド.md` の 14 を参照してください。

- **選び方（GPU の 3D を優先）**：
  - **特に高度な 3D 表現を求められていなければ、GPU の 3D（moderngl）を優先します**。
  - GPU の 3D（`gl_cards3d`・`gl_particles3d`・`gl_lightrays`）は 1 コマ数十ミリ秒で、プレビューでその場で描けます。
  - **立体の文字は部品に入れていません**（決まった形の 3D の文字はチープに見えるため同梱せず、その場で作ります）。必要なときは、その作品の場面に合わせて作品の `effects/` にその場で書きます（`docs/エフェクトの書き方.md` の「3D のエフェクト」）。
  - Blender の 3D（`blender3d`。初めて描くコマは数秒〜、ためて使い回す）は、反射・影・ガラス・被写界深度・作り込んだ形などを頼まれたとき、または GPU の 3D では明らかに足りないときだけ使います。迷ったら GPU の 3D で作って見せ、足りなければ Blender を提案します。
- **なじませの必須調整**：
  - **3D は、そのままでは極めてチープに見えやすいため、場面になじむまで慎重に調整するのが必須です**。
  - どちらの 3D でも既定の値のまま出さず、場面の色・明るさ・光の向きに合わせる、質感（つや・テクスチャ。生成した絵を面に使ってよい）、被写界深度・ぼかし・モーションブラー、影・映り込み・ブルーム、上から粒子・グレイン・色の手直しをかけて画面となじませる、動きの速さ・イージング・カメラの揺れを調整します。前後のカットと並べた静止画を何枚も見て、浮いて見える・おもちゃっぽいなら直します。
- **作品への導入**：
  - `effects_lib/common/<名前>.py` を作品の `effects/` に写します（編集画面の「エフェクト」タブ →「部品の置き場」→「作品に入れる」でも同じ。`blender3d` は場面のひな形 `templates/3d/*.py` も作品の `3d/` に写ります）。新しい作品には配りません（`FIRST_EFFECTS` に入れていない）。
  - 偽マリアのエフェクト集（`effects_lib/false_maria/fm_*.py`：光とトーンマップ・外周ネオン・シャッターの白フラッシュ・ガンマと彩度・暗転とクレジット・ハート。素材も人のマスクも不要）も同じ置き場から同じように入れられます（`docs/エフェクトの書き方.md` の「偽マリアのエフェクト集」）。
- **Blender の場面を組む手順**：
  1. 作品の `3d/<名前>.py` を書く（ひな形 `templates/3d/logo.py` を写して直す。作品の外のファイルを `scene` に指さない）。
     - 決まり：`build(scene, args)` は 1 回だけ場面を組み、`frame(scene, t, args)` はコマごとに `t`（クリップの頭からの秒）だけで形を決めます（前のコマを覚えない・乱数は決まった種）。
     - 道具：`import mittler_bpy as mb`（`pyengine/mittler/blender_kit.py`：`clear`・`camera`・`orbit_pos`・`look_at`・`studio`（3 灯）・`light`・`world`・`material`・`text3d`・`letters`（1 字ずつ・ロゴの組み上がり）・`floor`（`catcher=True` で影だけ受ける床）・`smooth`・`ease_out`・`back_out`）。座標は Blender のまま（z が上・−y が手前）。書体はファイルを渡します（日本語の字は書体が必要）。
  2. タイムラインに `blender3d` のクリップを置く（`params.scene` にそのファイル、`args` に字や色）。プレビューは下描き（`draft_samples`・`draft_scale`）で表示されます。
  3. 確かめる：`python -X utf8 -B -m mittler stills <tl> --at <秒> --out <フォルダ> [--blender <blender.exe>]`（本番の品質で描いて `work/3d/` にためる）→ 絵を Read で見ます。重い場面は `samples` を下げて試し、GPU を長く占めないようにします（ユーザーが同じ PC を使っていることがあるため）。
- **決定論性と環境差・停止挙動**：
  - GPU の 3D は同じ PC・同じ設定なら同じ時刻で同じ絵になります（`tools/smoke_3d.py --require-gl`）。Blender は描き直すと数画素違うことがあるため、ためた絵を使い回して一致させています（プレビュー・静止画・書き出し・並列数によらず、ためた同じファイルを読む）。
  - **3D がある作品の例外**：別の PC・別の GPU・別のドライバーでは画素の値が少し違うことがあります。3D のある作品で「直す前と静止画の SHA が同じ」を確かめるときは同じ PC で比べます。**3D を使わない作品の絵は 1 ビットも変わりません**（3D の部品は使うときに初めて読みます）。
  - 止まり方：GL が無い PC では「3D の描画が使えない（理由）」、Blender が無ければ「Blender が見つかりません」で、その時刻・書き出しが止まります（黙って抜かさない）。書き出しの「止める」・サーバーを閉じると Blender も止まります。

## 7.75 HTML のレイヤー（2026-11-18）

- **用途とひな形**：エフェクト `html` は、作品の `html/<名前>/index.html` を Chromium でコマごとに描いて重ねます。文字の動き・モーショングラフィック・パーティクル・three.js の 3D をその場で書くときに使います。ひな形は「作品に入れる」で `html/kinetic`・`html/particles3d`・`html/shapes3d`（three.js は `html/vendor/`）が入ります。**ひな形をそのまま使わず、場面に合わせて書き直します**（色・動き・質感・光）。
- **決まり**（くわしくは `docs/エフェクトの書き方.md` の「HTML のレイヤー」）：ページの `window.mittler` の `onFrame((t, args) => …)` で `t` だけから描く（差分・積み上げで動かさない）・背景は透明・ライブラリは `html/vendor/` に置く（外の URL は読めない。新しいライブラリを取ってくるときは先にユーザーに言う）・読めるのは作品の `html/` と `assets/` のみです。
- **確認方法**：`python -X utf8 -B -m mittler stills <tl> --at <秒> --out <フォルダ>` で静止画を見て確認します（前後のカットと並べる）。JavaScript のエラーは理由つきで止まります。

## 8. 音・セリフ

- **効果音・環境音**：ライセンスが動画に合う素材を使い、使う前に配布ページでライセンスを確かめ、出典を `work/research.md` に書きます。
- **動画の音と `link`**：動画（映像クリップ）の音は、別の `audio` クリップ（`assets/video_audio/<名前>.wav`、`from_video` のトラック）に入っており、`link` で動画とつながっています。動画を切る・動かす・消すときは、同じ `link` の音のクリップも同じように操作します（編集画面は自動でそうします）。動画の `in`・`start`・`dur` と音の値は同じです。
- **TTS クリップの演技・字幕・テイク**：
  - **演技**：キャラの声（スタイル）はそのままにして、そのシーンだけの演技は `delivery_style` に書きます（Gemini にはスタイルのあとに「 / 」でつないで送信。dialogue-video の `delivery_style` と同じ）。演技タグ（`[whispers]` など）の使い方・`delivery_style` との分け方は **`docs/GeminiTTSの演技タグ.md`** を参照してください。
  - **セリフから字幕**：編集画面の「セリフから字幕を作る」は、`text` から演技タグ `<…>` を外した文で `subtitle` クリップを作ります（`from_tts`＝セリフの id、`from_tts_text`＝作ったときの文。文がこれと違えば手で直したとみなして、作り直しで上書きしません）。
  - **テイクと一括生成**：テイク（`takes`）を積んで `activeTake` で選びます。テイクの WAV は `assets/voice/<クリップ id>_t<n>.wav` です。台本からセリフを並べたら、ユーザーは編集画面の「未生成のセリフを全部生成」（文があってテイクが無いものを時間順に 1 本ずつ）、AI は `python .mittler/api.py . tts-all --wait`（7.53）で生成できます。「全部を再生成」（2 回押し）は、テイクがあるものも含めて全部に新しいテイクを足します（前のテイクは残る）。
- **TTS エンジンと読み辞書**：
  - **Gemini TTS は文字を Google に送ります**（鍵は Windows の資格情報マネージャーの `ps:GEMINI_API_KEY`、値は表示しない）。VOICEVOX はその PC の `127.0.0.1:50021` です。ユーザーの事前の許可（0 の計画の OK）があれば、AI は好きなときに使ってよく、リトライもして構いません。
  - Gemini TTS の部品は `tools/gen/gemini_tts.py`（このリポジトリの中。どの PC でも同じ）。読み辞書は作品の `pronunciation.json`（足すのはユーザーが単語と読みを言ったときだけ）です。
- **速さ（生成のあと）と重なり**：
  - 速さはクリップの `tempo`（無ければキャラ設定の `tts.tempo`、無ければ `1`。`0.5`〜`2`）で指定します。生成後に ffmpeg の `atempo`（高さは変えない）をかけ、テイクに `tempo` を残します。次に生成したテイクから効きます（前のテイクはそのまま）。API は `tts <セリフ> --tempo 1.15`（クリップに書いてから生成）。プリセットのメモに「生成したあと atempo=1.15」とあるキャラは、キャラ設定の `tts.tempo` に `1.15` を設定します。
  - 声の長さでクリップの長さが決まります（`dur`＝テイクの長さ。動画の外まで伸びれば動画の長さも伸びる）。**同じトラックの次のセリフに重なると**、編集画面のクリップに注意の印、API の `tts` の結果の `overlaps` に相手の `id` が出ます。重なりは直します（次のセリフを動かす・速さを上げる・文を短くする）。別のトラック（別のキャラ）との重なりは、掛け合いでわざと重ねることがあるため印を付けません。
- **ミックスとノーマライズ**：
  - 書き出しの音は `mix.py`（ffmpeg）で処理します。クリップごとに切り出し・音量・フェード・遅延を行って混ぜ、`settings.audio.peak` で頭打ちします（`null` で頭打ちしない）。`settings.audio.mixer = "numpy"` の場合は dialogue-video（紙芝居）の `build.py` と同じ numpy 計算（足す順＝トラックの上から。作者の紙芝居の作品）になります。
  - 納品前の音のノーマライズ（dialogue-video の `run.ps1 normalize` と同じ loudnorm 2 パス）は `settings.export.loudnorm` で設定します（書き出しの最後。premaster も残る）。真のピーク（TP）が少し越えたら目標を下げて 1 回やり直し、それでも越えたら書き出しは止めずにログに `LOUDNORM_WARN` を出します（ユーザーに伝える）。

## 9. 書き出しと納品

- 編集画面の「書き出し」→ `output/<名前>.mp4`（サーバーの PC で描きます。SHA-256 も出力）。

## 10. Mittler 自体を直すとき

- **反映と配布版（VSIX）**：サーバー・拡張のコードを直したら、VS Code は「ウィンドウの再読み込み」で反映します（`package.json` を変えたら `tools/install_vscode.py` で入れ直し）。これは開発版（リポジトリを読む入口）の場合です。配布版（VSIX）で確かめるなら `python tools/build_vsix.py` で作り直して入れ直します（`docs/配布.md`。版の上げ方も記載）。
- **配布版の決まり**（`docs/配布.md` の 1）：
  - Mittler の置き場（配布版は拡張のフォルダ）は読み取り専用とし、動作中にそこへ書き込みません（`__pycache__`・キャッシュ・一時ファイル。Python の子プロセスは環境変数 `PYTHONDONTWRITEBYTECODE`、道具は `sys.dont_write_bytecode`）。書き込み先は作品・`globalStorage`・一時フォルダのみにします。
  - 作品のファイルに Mittler の絶対パスを書きません（`.mittler/` に集約）。
  - 新しいファイルを足したら、配布版に入れるか（`tools/build_vsix.py` の `INCLUDE`・`EXCLUDE`）を決めて `git add` します。
  - 直したら `tools/smoke_package.py` を流します。
- **エンジンの回帰確認**：エンジン（`pyengine`）を直したら、同じ作品・同じ時刻の静止画が直す前と**ビット単位で変わらない**ことを確かめます（直す前のエンジンと同じ時刻で描いて SHA を比べる。手元に本物の作品があれば、それでも確認）。
- **テストと文書の同時更新**：直したら smoke test（7）を流し、README・このガイド・`docs/タイムライン形式.md`・`docs/ARCHITECTURE.md` を合わせて直します（文書は `tools/smoke_docs.py` で確認）。
- **UI トークンとステータス表示**：編集画面の見た目は `editor/editor.css` の頭のトークン（色・余白・角丸）を使います（色を決め打ちで足さない。VS Code のテーマの色は `editor/ui.js` が受けます）。上の 1 行の知らせ（`setStatus(文, 種類)`）の種類（`ok`・`busy`・`warn`・`bad`・`act`）は**呼ぶ側が渡します**（2026-11-13〜。前は文の言葉で決めていた。英語の画面でも同じ種類になるように）。`bad` は右下にも残ります。
- **画面の言葉は辞書の鍵で**（2026-11-13〜）：
  - `editor/i18n/en.json`（英語）と `ja.json`（日本語）に同じ鍵を足します。
  - 参照方法：編集画面は `$t('鍵', {名前: 値})`（あとで訳し直す文は `$L`）、`index.html` は `data-i18n`・`data-i18n-title`・`data-i18n-ph`・`data-i18n-aria`、サーバーは `$t`・鍵つきの例外 `I18N.keyedError`（`server/i18n.js`）、Python は `pyengine/mittler/i18n.py` の `t`（環境変数 `MITTLER_LANG`）。
  - 英語の複数形は `{"one": …, "other": …}`（`n` が 1 のとき `one`）。言葉を切り替えたら作り直す部分は `MITTLER_I18N.onChange` で処理します。ログ・コメント・smoke の文は鍵にしません。
  - 直したら `tools\smoke_i18n.py` を流します。エフェクトの英語の名前・説明は `docs/エフェクトの書き方.md`（`label_en`・`DOC_EN`）を参照してください。
- **画面に絵文字を使わない。印は Lucide の線のアイコン**（絵文字をやめ、モノグラムのアイコンで統一）：
  - 1 色（字の色）で、線の太さがそろったアイコンを使います。
  - 呼び出し方法：JS は `MITTLER_ICON('名前')`（`editor/ui.js`。`<i class="ic" data-ic="名前">`）、ボタンの「アイコン＋名前」は `MITTLER_ICO('名前', 名前の文)`、`index.html` は `<i class="ic" data-ic="名前" aria-hidden="true"></i>`、辞書の文の中は `{icon:名前}`（画面に出たところで `ui.js` がアイコンに置きかえる）。
  - **文字しか出せない所（ツールチップの `title`・押せない理由・VS Code の知らせ・設定の説明・ログ）には印を書かず、言葉だけ**にします（サーバー・エンジンの `t` は印を外す）。
  - 名前は Lucide の名前（`https://lucide.dev/icons`）。新しく使うときは、`THIRD_PARTY_NOTICES.md` の版の `lucide-static` の配布物から SVG を中身を変えずに `editor/icons/` へ写し、`editor/editor.css` の `.ic` の一覧に 1 行足します（ほかのアイコン集を混ぜない）。
  - 直したら `python -X utf8 tools/smoke_icons.py`（置き場・名前・絵文字）と `smoke_i18n` の (g)（画面に絵文字が残らない）を確認します。エフェクトが絵として描く字（星など）は対象外です。
