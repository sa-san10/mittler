# インストールガイド（Mittler を入れる・入れ直す・PC を移す）

短い手順は [スターターガイド](スターターガイド.md) の 1 をご覧ください。この文書では、インストールの詳しい手順に加えて、PC ごとの設定・セキュリティ・マスター書き出し用の道具・名前の一覧をまとめています。**Windows 専用**です（詳細は 12 の終わりを参照）。

- PC ごとの設定（描く python・解析の python・ffmpeg・VOICEVOX・プリセットなど）の一覧は **12「設定の一覧」** にまとめています。
- インストール時に使うファイル（初期設定の確認スクリプト・Python パッケージ一覧など）は、リポジトリの **`setup/`** にあります。

**入れ方は 2 通りあります**（2026-11-13 から。詳しくは 2 と [配布](配布.md) を参照してください）。

- **配布版（中身を全部入れた VSIX）**：利用する方向けです。VSIX を入れて、VS Code のコマンド **「Mittler: 初期設定」**（3）を実行します。リポジトリは不要です。
- **開発版（clone したリポジトリを読む入口）**：Mittler 本体を直す方向けです。まず **`python setup\mittler_setup.py`** を実行してください。必要なものがそろっているかを確認し、足りないものと入れ方を表示します（環境は何も変更しません。詳細は `setup/README.md`）。

下の 0〜3 は、これらを手動で行う場合の手順です。

**この文書で使う表記とおすすめフォルダ構成**

| 表記 | 意味 |
|---|---|
| `<mittler>` | Mittler の場所（開発版はこのリポジトリを置いた場所、配布版は VS Code の拡張の置き場。作品の `.mittler/env.json` の `mittler_dir` にも書かれます） |
| `<works>` | 作品をまとめて置くフォルダ |
| `<venv>` | 描画用の Python の環境 |
| `<av_ai>` | 解析用の Python の環境 |

配置場所は自由ですが、次のように並べておくと迷いません（開発版では、キャラのプリセットはリポジトリの**隣**の `presets\characters\` が既定の場所になります。詳細は 6）。

```text
<スタジオ>\                       ← 名前・場所は何でもよい
  ├ mittler\                      ← このリポジトリ（<mittler>）
  ├ presets\characters\           ← キャラのプリセット（下の 6。なくてもよい）
  └ works\<作品>\                 ← 作品（<works>\<作品>。タイムライン・effects は git、素材 assets は自分の控えから）
```

## 0. 要るもの

| もの | 何に使うか | 入れ方の例（winget はユーザーごと・確認なし） |
|---|---|---|
| Git | Mittler や作品の取得、作品の取り消し（`git add -A`） | `winget install Git.Git --scope user --silent --disable-interactivity` |
| Python 3.12 以上 | 描画（Python エンジン）・補助の道具・フック（3.12 と 3.14 で動作確認済み） | `winget install Python.Python.3.14 --scope user --silent --disable-interactivity` |
| ffmpeg（full build・libass 入り） | 書き出し・サムネ・波形・音の取り出し・ASS 字幕（9.0.2 の gyan.dev full build で動作確認済み） | `winget install Gyan.FFmpeg --scope user --silent --disable-interactivity` |
| VS Code | 編集画面（Mittler の拡張）。**Node は不要**（VS Code 内蔵の Node で動作） | `winget install Microsoft.VisualStudioCode --scope user --silent --disable-interactivity` |
| エージェント（Claude Code など・任意） | 右の列でエージェントに依頼する。フック（編集画面の今を添える）とスキルは Claude Code 向け | VS Code の拡張機能で「Claude Code」（Anthropic）などを導入 |
| VOICEVOX（任意） | セリフの VOICEVOX 音声。`http://127.0.0.1:50021` で動いていれば利用可能 | VOICEVOX を入れて起動しておく |

> 新しく開いたターミナルで `python`・`ffmpeg`・`ffprobe`・`git` が実行できる（PATH が通っている）ことを確認してください。フックは `python -c "…"` で動くため、そのアカウントで `python` が見つかる必要があります（4）。

## 1. Mittler を取ってくる（開発版だけ）

```powershell
git clone https://github.com/sa-san10/mittler.git <mittler>
```

- 置く場所はどこでも構いません（拡張機能はその場所の `extension.js` を読み込みます）。
- 更新するときは `git pull` を実行してください。
- 配布版（2 の「配布版」）を使う場合、この手順は不要です。

## 2. VS Code に拡張を入れる

### 配布版（VSIX）

1. VSIX（`mittler-<版>.vsix`）を用意します。GitHub の Releases からダウンロードするか、リポジトリで `python tools/build_vsix.py` を実行して作成します（`dist/` に出力されます。詳細は [配布](配布.md)）。
2. VS Code の「拡張機能」ビュー → 右上の「…」→「**VSIX からのインストール…**」から VSIX を選びます。コマンドで入れる場合は次のとおりです。
   ```powershell
   code --install-extension <mittler-<版>.vsix> --force
   ```
   開発版のリポジトリがある場合は、`python <mittler>\tools\install_vscode.py --vsix <VSIX>` でも同じ結果になります。
3. VS Code で「ウィンドウの再読み込み」を行い、コマンド「**Mittler: 初期設定**」（3）を実行します。

配布版についての補足：

- 中身はすべて拡張機能の置き場（`%USERPROFILE%\.vscode\extensions\sa-san10.mittler-<版>\`、Remote-SSH の接続先は `~/.vscode-server/extensions/…`）に入ります。リポジトリは不要です。
- **更新**：新しい VSIX を同じ手順で入れます（置き場ごと入れ替わります）。作品は修正不要で、開けば `.mittler/` が新しい場所に合わせて書き直されます（4）。
- 拡張機能の置き場は読み取り専用として扱います（Mittler は動作中にそこへ書き込みません）。置き場の中のファイルを直接編集しないでください。

### 開発版（リポジトリを読む入口）

```powershell
python <mittler>\tools\install_vscode.py
```

`python setup\mittler_setup.py --install-extension` でも同じです（使用する python は何でも構いません）。

- 入るのは「このリポジトリの `extension.js` を読むだけの入口」です（拡張の ID は `sa-san10.mittler`）。
- リポジトリを `git pull` したあとは、VS Code で「ウィンドウの再読み込み」をするだけで反映されます（`package.json` が変わったときだけ、上のコマンドをもう一度実行してください）。

### どちらでも

- `*.cut.json` を開くと編集画面が表示されます。
- コマンド「Mittler: 新しい作品を作る」も使えます（「ファイル → 新しいファイル…」にも同じ項目が出ます）。

### 開発版と配布版を入れかえる

どちらも拡張の ID は `sa-san10.mittler` なので、**後から入れたほうが前のほうを置き換えます**（先にアンインストールする必要はありません）。入れ替えたら「ウィンドウの再読み込み」を実行してください。

| したいこと | 実行するコマンド |
|---|---|
| 開発版 → 配布版 | `code --install-extension <mittler-<版>.vsix> --force`（または `python <mittler>\tools\install_vscode.py --vsix <VSIX>`） |
| 配布版 → 開発版 | `python <mittler>\tools\install_vscode.py` |
| 外す | `code --uninstall-extension sa-san10.mittler`（`python <mittler>\tools\install_vscode.py --uninstall` も同じ） |

- どちらが入っているかは、`python <mittler>\setup\mittler_setup.py` の最初の行（配布版／開発版）、または作品の `.mittler/env.json` の `mittler_kind`（`vsix`・`dev`）で確認できます。
- 設定（`mittler.*`）・作品・描く python の設定は、そのまま引き継がれます。
- 作品のフックや `CLAUDE.md` が開発版リポジトリの絶対パスを名指ししている以前からの作品でも、リポジトリが残っていれば配布版に切り替えてもそのまま動きます（15）。

## 3. 描画の Python（Python エンジン）

### 入れた直後の知らせ（0.4.0〜）

拡張機能は VS Code の起動完了後（`activationEvents` の `onStartupFinished` で動作するため起動を遅くしません）にも起動し、**その版で初回のときだけ**短い確認を行います。確認内容は「描く python が numpy・OpenCV・Pillow を import できるか」「ffmpeg が見つかるか」です。探索順は描画時と同じ（設定 → 既定の場所 → PATH）で、静止画は描かないため数秒で終わります。

- **初めて入れたとき**：足りないものがあれば「Mittler を使う準備：（足りないもの）が見つからない」とボタン「Mittler: 初期設定」「あとで」が表示されます。すべてそろっていれば歓迎の通知と「新しい作品を作る」ボタンが表示されます。
- **版を上げたとき**：足りないものがある場合だけ通知されます。
- **表示の制御**：一度表示したら（どのボタンを押しても、閉じても）その版では再表示されません（表示済みの版は設定ではなく拡張の globalState に保存されます）。作品を開いたときの案内（下の最後の項目）は別に出ます。
- **言語と実装**：表示言語は設定 `mittler.language` に従います（既定は英語。編集画面と同じ）。実装は `extension_setup.js` の `firstRun`、テストは `tools/smoke_package.py` です。

### コマンド「Mittler: 初期設定」（配布版でも開発版でも）

VS Code のコマンドパレット（Ctrl+Shift+P）から「**Mittler: 初期設定**」を実行します（入れた直後の通知ボタンからも開けます）。

1. `setup/mittler_setup.py --json` で環境を確認します（環境は何も変えません。試しの静止画を 1 枚描くため少し時間がかかります）。結果は VS Code の「出力」パネルの「**Mittler**」に一覧表示されます（そろっているもの・足りないもの・入れ方）。
2. 描ける python が見つからない場合は「**描く python を入れる…**」が表示されます。押すと、入れる内容（「描画だけ」か「描画＋GPU の 3D」）を選び、導入するパッケージ名と版を確認する画面が出ます。「入れる」を押したときだけ、VS Code の拡張の保存場所（globalStorage の `render-venv`）に venv を作り、`setup/requirements-engine.txt`（選べば `setup/requirements-3d.txt` も）を PyPI からインストールし、ユーザー設定 `mittler.render.python` をその python に設定します。開いているタイムラインは、開き直すか「ウィンドウの再読み込み」を行うと有効になります。
3. 描く python がその venv で、GPU の 3D（moderngl）が入っていない場合は「GPU の 3D（moderngl）を足す…」が表示されます（押したときだけ導入します）。

補足：

- Python・ffmpeg・Git・VS Code 本体は自動インストールしません（入れ方の winget コマンドを出力に出します）。Python が見つからない場合は、コピーできるコマンドを通知します。道具を動かす python の探索順は、設定 `mittler.tools.python` → PATH の `python` → `py` です。
- Blender（3D）は、利用する方向けの案内のみ表示します（14）。
- 作品を開いたときに描ける python が見つからない場合は、このコマンドへの案内が 1 度表示されます。

### 手で入れる

```powershell
py -3.12 -m venv <venv>
<venv>\Scripts\python.exe -m pip install -r <mittler>\setup\requirements-engine.txt
```

`python setup\mittler_setup.py --install-venv <venv>` でも同じ処理を行います。

- **入るパッケージ**：numpy・opencv-python-headless・Pillow・onnxruntime（`setup/requirements-engine.txt`。該当バージョンが無い環境では `==` を外してください）。
- **VS Code の設定**：作成した python を `mittler.render.python` に指定します（例：`"mittler.render.python": "<venv>\\Scripts\\python.exe"`）。ffmpeg が PATH に無い場合は `mittler.render.ffmpegDir` も設定してください。設定変更後は「ウィンドウの再読み込み」を行います。
- **未設定時の探索順**：タイムラインの `render.python`（書いてある場合。検証を通ったもの：11）→ 無ければ既定の場所（`server/defaults.js` の `renderPython`）→ PATH の `python` の順に探し、numpy・opencv・Pillow を import できた最初のものを使います。PATH の `python` にパッケージが入っていれば設定は不要です。
- **起動前チェック**：設定した python も起動前に確認し、存在しない・import できない場合は、理由と修正すべき設定名を編集画面に表示します。
- 新しい作品のタイムラインには `render.python` を書きません（以前の作品に書かれている値はそのまま使用します）。

### どの PC で描くか

描画は常に拡張機能（VS Code）が動いている PC で行います。描く python や ffmpeg のフォルダは PC ごとの VS Code 設定で決めます（ほかの設定も含めた一覧は 12「設定の一覧」）。

別の PC（GPU のある PC など）で描画したい場合は、10「リモートで使うには Remote-SSH」を参照してください。

> 拡張機能が自分で ssh して描く「ssh のモード」は 2026-10-30 に廃止されました。以前の作品のタイムラインに `render.host`・`render.remote` が残っていても使用しません。

## 4. Claude Code の設定（だいじ）

エージェントが最初に読む入口は、リポジトリ根の `AGENTS.md` です（Claude Code は根の `CLAUDE.md` からそれを読み込みます）。エージェントに「**Mittler の初期設定をして**」と頼むと、`setup\mittler_setup.py` で確認し、足りないものを報告します（[スターターガイド](スターターガイド.md) の 2）。

### Claude Code のスキルを入れる

空のフォルダで「Mittler で新しいプロジェクトを始めたい」と伝えるだけで空の作品を作れるスキルを導入します。

```powershell
python <mittler>\setup\mittler_setup.py --install-skill
```


- `skills/mittler-new-project/` が `~/.claude/skills/` にコピーされ、隣に Mittler の場所（`mittler_dir.txt`）が書かれます。何回実行しても問題ありません。
- 配布版の置き場から入れた場合も、拡張機能の更新によって書かれた場所が無くなっていれば、入っている Mittler 拡張のうち新しいものを自動で探します。

### 作品に入る Claude Code 向けの設定

作品を作ると次のファイルが自動で入ります（手動で配置する必要はありません）。2026-11-13 以降、**作品のファイルには Mittler の場所（絶対パス）を書かない**仕組みになっています。

| 場所 | 中身 |
|---|---|
| 作品の `.claude/settings.json` | フック（UserPromptSubmit）：`python -c "…"`。python が環境変数 `CLAUDE_PROJECT_DIR`（Claude Code が渡す作品の場所。無ければカレントフォルダ）から上にたどって `.mittler/hook.py` を探して実行します（無ければ何もしません）。話しかけるたびに、編集画面の今（選択中のもの・時刻・書き込み・git の注意）を添えます。前からある作品は `python "<mittler>/tools/mittler_state.py"` の絶対パスのままでも動作します（15）。 |
| 作品の `AGENTS.md`・`CLAUDE.md` | `AGENTS.md` はその作品の説明と決まり（エージェント共通。Mittler の場所は `.mittler/env.json` と書くだけ）、`CLAUDE.md` は Claude Code の入口で `@AGENTS.md` と `@.mittler/guide.md` を読み込みます（どちらも作品内にあるため読み込み許可は不要。`templates/project/` から生成）。 |
| 作品の `.mittler/`（git に入らない） | 拡張機能が作品を開くたびに、その PC 用に生成します（下の表）。 |
| Mittler の `docs/スターターガイド（AI用）.md` | Claude が Mittler を扱うときの説明書（タイムラインの形・直し方・やってはいけないこと）。作品からは写しである `.mittler/guide.md` を通じて読みます。 |

### 作品の `.mittler/` に書き出されるもの

- **書き出されるタイミング**：拡張機能（サーバー）が作品を開いたとき（描く python が決まったらもう一度）と、新しい作品を作ったとき（`tools/new_project.js`）。
- **扱い**：中身が同じなら書き換えません。手動で編集しないでください（次に開いたときに上書きされます）。生成元は `server/project_env.js` です。

| ファイル | 中身 |
|---|---|
| `env.json` | `mittler_dir`（Mittler の場所）・`mittler_version`・`mittler_kind`（`vsix`＝配布版・`dev`＝開発版）・`docs_dir`・`tools_dir`・`pyengine_dir`・`render_python`（描く python）・`ffmpeg_dir`・`blender`・`language`・`commands`。鍵・トークンは入れません（トークンは従来どおり `server.json`）。 |
| `guide.md` | Mittler の AI 用ガイドの写し（先頭に、どの版の写しかを 1 行記載）。 |
| `hook.py` | フックの中継：`env.json` の場所にある `tools/mittler_state.py` をこの作品に対して実行します。 |
| `api.py` | 編集画面に頼む道具の中継：`python .mittler/api.py . <コマンド>`（`tools/mittler_api.py` と同じ引数）。 |
| `engine.py` | 描画エンジンの中継：`python .mittler/engine.py stills <タイムライン> --at <秒> --out <フォルダ>`（`env.json` の描く python で `python -m mittler …` を実行。まだ編集画面で描いておらず空の場合は、既定の場所・PATH の python のうち描けるものを使用。ffmpeg のフォルダも PATH に追加）。 |
| （前から）`server.json`・`state.json`・`current_frame.jpg`・`annotations/`・`thumbs/`・`waves/` ほか | 編集画面のサーバーが書き出すファイル群（11）。 |

補足：

- 中継スクリプト（`hook.py`・`api.py`・`engine.py`）は、`env.json` に書かれた場所に Mittler が無い場合（拡張を更新して、まだ作品を開いていない場合など）、インストールされている Mittler 拡張のうち新しい版を使います。
- まだ一度も開いていない作品（clone した直後や別 PC からコピーした直後）には `.mittler/` が無く、フックは何もしません。エージェントは、ユーザーに編集画面で 1 度開いてもらうよう案内します（作品の `AGENTS.md` に記載済み）。
- フックを `python -c "…"` としているのは、PC によってフックを実行するシェルが異なるためです（Git Bash・cmd・PowerShell。検証環境では `$CLAUDE_PROJECT_DIR` は展開され、`%CLAUDE_PROJECT_DIR%` は展開されませんでした）。python 内で環境変数を読むことでどのシェルでも同じ動作になります。なお、Claude Code を作品内のサブフォルダで起動すると、作品の `.claude/settings.json` は読み込まれません（以前の絶対パス形式のフックも同じです）。

### PC を移したとき・Mittler の場所が変わったとき

新しい作品（2026-11-13〜）は何もしなくて構いません（編集画面で開けば `.mittler/` が書き直されます）。

以前からある作品で「UserPromptSubmit operation blocked by hook … can't open file」と表示された場合は、フックを現在の形式にそろえます（15）。

```powershell
python <mittler>\tools\fix_hooks.py <works>
```

- `--dry-run` を付けると、書き換えずに変更内容だけ確認できます。
- 実行前に作品ごとに `git add -A` を行ってください。
- 以前の絶対パス形式にしたい場合は `--absolute` を付けます。

## 5. Gemini の鍵（セリフの Gemini TTS）

API キーは **Windows の資格情報マネージャー** の汎用資格情報 `ps:GEMINI_API_KEY` に登録します（`.env` ファイルは作らず、値を画面・ファイル・チャットに出さないでください）。

次のどちらかの方法で登録します。

- PowerShell の SecretManagement（CredMan の保管庫）がある場合：`Set-Secret -Name GEMINI_API_KEY`（聞かれたら鍵を貼り付け）
- 無い場合：`cmdkey /generic:ps:GEMINI_API_KEY /user:gemini /pass`（聞かれたら鍵を貼り付け）

登録できたか確認します（値は表示されず文字数のみ表示されます）。

```powershell
python <mittler>\setup\check-gemini-key.py
```

環境変数 `GEMINI_API_KEY` が設定されている場合は、そちらが優先されます。

### OpenAI の鍵（動画化予定の絵を OpenAI の Image API で作るとき。使わないなら要らない）

Gemini と同じく、資格情報マネージャーの汎用資格情報 `ps:OPENAI_API_KEY` に登録します（値を画面・ファイル・チャットに出さないでください）。

- **いちばん確実な方法**：鍵だけをコピーしてから次を実行します。
  ```powershell
  python <mittler>\tools\gen\credman_secret.py --set-from-clipboard OPENAI_API_KEY
  ```

## 10. リモートで使うには Remote-SSH

描画は常に拡張機能が動いている PC で行います。別の PC（例：GPU のある PC。以下 `render-pc` と呼びます）の作品を手元の PC から操作したい場合は、VS Code の **Remote-SSH** でその PC に接続し、接続したウィンドウの中で作品を開きます。

拡張機能・編集画面のサーバー・描画・書き出し・解析・動画化予定の生成ジョブ・Claude Code はすべて接続先 PC で動き、編集画面は VS Code のポート転送によって手元のウィンドウに表示されます（拡張機能が自分で ssh して描く「ssh のモード」は 2026-10-30 に廃止しました）。

1. **手元の PC**：VS Code に拡張機能「Remote - SSH」（`ms-vscode-remote.remote-ssh`）を入れ、`~/.ssh/config` に接続先を書きます。
   ```sshconfig
   Host render-pc
       HostName <その PC の名前か IP>
       User <その PC のアカウント>
       IdentityFile ~/.ssh/<鍵>
   ```
2. VS Code のコマンド「Remote-SSH: Connect to Host…」→ `render-pc` を選びます。初回接続時は VS Code Server が接続先に自動で入ります。
3. 接続したウィンドウで、接続先側に 1〜3（Mittler・拡張機能・描画の Python）がそろっている状態にします。拡張機能は接続したウィンドウのターミナル（接続先上で動作）で `python <mittler>\tools\install_vscode.py` を実行して入れます。描く python などの設定は、接続先の設定（「リモート [SSH: render-pc]」）に書きます。
4. 「フォルダーを開く」で接続先の `<works>\<作品>` を開き、`*.cut.json` を開きます。

リモート利用時の補足：

- 生成とセリフは接続先 PC で動くため、接続先アカウントに Codex CLI（と `~/.codex`）・VOICEVOX・Gemini の鍵・Google ドライブ（H3 の受け渡し）が必要です。
- 公開鍵認証でログインした ssh セッション内からは Windows の資格情報マネージャーを読めません（エラー 1312 を確認済み）。Gemini TTS は環境変数 `GEMINI_API_KEY` が設定されていればそちらを使用します。
- **画面を使わずに確認する場合**：接続先で `node server\main.js <作品>\xxx.cut.json --port <N>` を起動し、手元から `ssh -L <N>:127.0.0.1:<N> render-pc` で転送して `http://127.0.0.1:<N>/…` を開きます（`tools/smoke_export.py --remote-project`）。

## 11. 安全（作品を開くと何が動くか・決まり）

作品を開くと、その作品の `effects/*.py`（エフェクトのコード）が描画の python で実行され、タイムラインに書かれた python（`render.python`・`settings.analysis_python`）も子プロセスとして起動します。

> **知らない人の作品は、必ず中を確認してから開いてください。** 2026-10-30 から、次の仕組みで保護しています。

- **信頼したフォルダでのみ動作（VS Code の Workspace Trust）**
  - `package.json` の `capabilities.untrustedWorkspaces.supported` は `false` に設定しています。
  - 信頼していないフォルダ（制限モード）では VS Code が Mittler を起動せず、`*.cut.json` は通常の JSON テキストとして開きます。念のため拡張機能側でも、信頼されていなければ作品を開きません。
  - 信頼するには、制限モードの帯から「このフォルダーを信頼する」を選びます。
- **編集画面のサーバー（`server/server.js`）**
  - `127.0.0.1` のみで待ち受け、Host ヘッダを検証します。
  - 起動ごとのトークン（作品の状態フォルダ `.mittler/` の `server.json`）が必要なリクエストは次のとおりです。
    - **書き込み（GET・HEAD 以外のすべて）**：ヘッダ `X-Mittler-Token` が必須です。
    - **副作用のある GET**（描画サーバーを起動する・ffmpeg／ffprobe を動かす・ファイルを書き出す）：`/api/status`・`/api/frame`・`/api/effects`・`/api/thumb`・`/api/wave`・`/api/assets`。ヘッダ `X-Mittler-Token` または `?token=` が必要です（`img` や CSS の `url()` はヘッダを付けられないため、編集画面からは URL に付けます）。
  - `/project/`（作品のファイル配信）では `.git` と状態フォルダ `.mittler`（トークンの `server.json`・`state.json` など）を配信しません（403）。大文字小文字の違い・名前の末尾の `.` や空白・`:` の後ろ・8.3 形式の短い名前であっても同じ場所なら拒否します。書き込みの記録は `/api/annotation?id=<id>&file=after.jpg|before.jpg|annotation.json` から取得します。
- **Suno の曲（2026-10-30）**
  - Mittler 自体は Suno を呼び出しません（鍵・OAuth を持たず、呼び出すのは Claude Code の Suno MCP です）。
  - 外部を開くのは「suno.com で聞く」（`POST /api/music/open`、トークン必須）のみで、許可する URL は `https://suno.com/song/<UUID>` 形式に限ります（それ以外は拒否）。VS Code 内では `vscode.env.openExternal`（未信頼ドメインは VS Code が確認）、単体実行時は PC の既定ブラウザで開きます。
  - 曲の納品（`POST /api/music/take`）は、素材の根の中にあるファイルだけを受け取ります（作品の外・`.git`・`.mittler` は拒否）。

### タイムラインに書かれた python

タイムラインの `render.python`（描く python）と `settings.analysis_python`（解析の python）は、起動前に `server/pyrender.js` の `checkPython` で検証します。

- **許可する条件**：**名前だけの python**（`python`・`python3` など、PATH から探すもの）、または **この PC に実在するファイルの絶対パスで、ファイル名が python**（`python.exe`・`python3.12.exe`・`pythonw.exe` など）のものだけを通します。相対パス・存在しないファイル・ファイル名が python でないもの（`cmd.exe` など）は使いません。
- **`render.python` の扱い**：
  - 検証を通らない場合は使用せず、PATH の python から描けるものを探します（ログに「タイムラインの render.python は使わない：理由」を出力）。
  - PC の設定（`mittler.render.python`・単体の `--render-python`）があれば、タイムラインの値は使いません。設定値と異なる場合は、サーバー起動時にログへ 1 度「タイムラインの render.python（…）は使わない：この PC の設定の python（…）で描く」と出力します。
  - 実際にどれを使うかは「描く python：…（この PC の設定／タイムラインの render.python／既定／PATH）」とログに出ます。
- **`settings.analysis_python` の扱い**：
  - PC の設定（`mittler.analysis.python`・単体の `--analysis-python`）があれば、タイムラインの値は使いません（異なればログに 1 度通知）。
  - PC の設定が無い場合は検証し、通らなければ解析を実行しません（解析ジョブが「タイムラインの settings.analysis_python を使わない：理由」で失敗します）。
  - 検証を通ったものを使うときは、ログに 1 度「解析の python：タイムラインの settings.analysis_python（…）」と出力します。
- **PC の設定の扱い**：VS Code の `mittler.*` や単体オプションは、その PC の利用者が書いたものとして検証をスキップします。

#### マスター書き出しの既定値とキャッシュ

マスター書き出し（機能追加案03 v2）の既定値は `server/defaults.js` の `master` にあります（並列の既定 `jobs: 0`＝自動 もここ。詳細は下の「マスター書き出しの並列」）。単体で `python -m mittler master` を動かすときの既定値は `pyengine/mittler/master.py` の `DEFAULTS` で同じ値になっています。

- RIFE のモデル `rife-v4.6`、および縮小フィルタ `area`（lanczos は星のまわりに暗い縁が出たため `area` を採用）は、`--rife-model`・`--down` で変更できます（設定項目にはしていません）。
- Real-ESRGAN と RIFE はこのリポジトリに含まれていません（PC ごとに導入します）。どちらも無い PC でも、映像素材が無い作品やアプスケも補間も不要な作品ならマスター書き出しできます。必要なのに無い場合は、書き出し前に「道具が無い」と理由つきで停止します。

マスター書き出しのキャッシュ（作品の `work/master/upscale`・`interp`）の仕様は次のとおりです。

- **残すファイル**：補間する素材は**補間ずみだけ**を残し（アプスケずみは補間に入れたら削除）、補間しない素材（fps が出力 fps 以上）は**アプスケずみ**を残します。補間の設定（fps・RIFE モデル）を変えて作り直す場合はアプスケからやり直しになります（作者の PC で素材 3 秒あたり約 7〜23 秒、1344×768 素材が最長）。
- **保存形式**：**H.264 を RGB のまま**（`libx264rgb`・crf 10・medium、ファイル名末尾 `_x264rgb10.mkv`）で保存します。わずかな劣化はありますが、マスター最終出力（area で 1080 へ縮小したもの）では見分けられない程度です（実道具での計測：PSNR 56〜62 dB、最大差 14/255、拡大した星のキラキラも同等に視認。書き出しの H.264 crf 18・4:2:0 自体の劣化は 36〜46 dB でそれより十分小さい）。サイズは以前の形式（FFV1・可逆）の 1/6〜1/10（平らな夜空のような絵は 1/144）です。
- **中間キャッシュと旧形式**：補間へ渡す途中のアプスケずみは従来どおり可逆（`_ffv1.mkv`、補間完了後に削除）です。単体実行の `--cache-fmt ffv1` で可逆形式にもできます（設定項目にはしていません）。旧形式のキャッシュ（名前に形式印が無い `*_60.mkv` など）は使わず新しく作り直し、古いものは上限掃除で古い順に消えます（すぐ消したい場合は、下にあるマスターの窓の詳細設定の「キャッシュ」→「削除」）。
- **キャッシュを使わずに作り直す**：マスターの窓の詳細設定チェック（既定はオフ）、または単体の `python -m mittler master … --fresh` を使います。書き出し開始時（書き出し前チェックと道具確認を通過したあと）に、その作品の `work/master/upscale`・`interp` 内のファイルと `hashes.json` をすべて削除してアプスケ・補間からやり直します（他作品のキャッシュには触れず、チェックで止まった場合は削除しません）。Real-ESRGAN・RIFE を入れ替えたとき、素材を同名・同サイズ・同更新時刻のまま差し替えたとき、キャッシュの絵がおかしいときに使います。
- **マスターの窓の詳細設定の「キャッシュ」→「削除」ボタン**：**今すぐ消すだけ**（`*.mkv` を削除。書き出しは実行しません）。次回のマスター書き出し時に必要な分を作り直します。

### アップスケールのモデル（アニメ／実写。2026-10-31）

アップスケールのモデルをアニメ用・実写用・なしから選べます。偽マリア（作者の MV 作品。下の計測値の多くはこの作品によるもの）を 4K で通した際、アニメ用の `realesr-animevideov3` が写真調の素材の細かい模様（ヒョウ柄・「神話」のスパンコール・リボンのラメの粒）を描き直して塗ったように平らにしてしまったことから追加した仕組みです。

| 名前 | モデル（Real-ESRGAN ncnn-vulkan の `-n`） | 倍率（`-s`） | 向くもの |
|---|---|---|---|
| アニメ（`anime`） | `realesr-animevideov3` | 2・3・4 の足りる最小（1344×768 なら 3 → 4032 を 3840 に縮小） | アニメ・イラスト・CG の絵。輪郭がくっきりする。写真の細かい模様・粒は描き直されて平らになる |
| 実写（`real`） | `realesrgan-x4plus` | 4 のみ（x4 で上げてから lanczos で長辺 3840 に縮小。1344×768 なら 5376 → 3840） | 写真・実写・写真のような生成動画。模様・粒・ラメを元の形のまま残す。アニメより約 11 倍時間がかかる |
| なし（60fps だけ。`none`） | 使わない（Real-ESRGAN を呼ばない。無い PC でも可） | — | 4K は不要で 60fps の滑らかさだけほしいとき（下の「アップスケールなし（60fps だけ）」） |

詳細と挙動：

- **画面上の名前（2026-10-31 夜の窓刷新から）**：マスターの窓の「画質」では、**標準**＝`none`・**高画質（アニメ）**＝`anime`・**高画質（実写）**＝`real` と表示します。映像クリップの欄では「マスター画質」です。内部用語（Real-ESRGAN・RIFE・キャンバスの倍率・キャッシュの場所と上限）は基本画面には出さず、各項目のツールチップにのみ記載しています。
- **優先順（強い順）**：
  1. 映像クリップの欄の「マスター画質」（クリップの `upscale`。動画化予定クリップは JSON の `upscale`）
  2. 単体実行の `mittler master --upscale anime｜real｜none`
  3. マスターの窓の「画質」（作品ごと。タイムラインの `settings.master.upscale` に保存。窓から始めた書き出しは窓で選んだ値を `--upscale` でも渡すため、保存反映前でも見えているとおりになります。2026-10-31）
  4. PC の設定 `mittler.master.esrganModel`（単体は `--esrgan-model`）
  5. 既定 `realesr-animevideov3`
  - どこにも指定が無い作品は**従来と 1 ビットも同じ**結果になります（同じ引数・同じキャッシュ名・同じ MP4）。未知の名前は書き出し前に名指しで止まります（`MASTER_STOP` の kind `upscale`）。
- **モデル定義と検証**：名前→モデル・モデル→倍率の対応は `pyengine/mittler/master.py` の `UPSCALE_KINDS`・`ESRGAN_MODELS` の 1 か所にまとめています（編集画面の表示は `server/defaults.js` の `masterUpscale` で、一致を `tools/smoke_same.py` が検査します）。`realesrgan-x4plus-anime`（x4 のみ）も表にあり、`--esrgan-model` で利用可能です。表に無いモデルは従来どおり 2・3・4 の足りる最小を使います。
- **モデルファイルの確認**：exe の隣に `models/` がある場合、必要なファイル（`realesr-animevideov3-x3.param`・`realesrgan-x4plus.param` など）が不足していれば描き始める前に名指しで止まります。下の「入れ方」にある zip（v0.2.5.0）には両方含まれています。
- **モデルごとのキャッシュ**：キャッシュ名にモデルが入ります（`<ハッシュ>_<モデル>_60_x264rgb10.mkv`）。モデルを変えるとアプスケ対象素材は ①② からやり直しになります（前モデルのキャッシュは残り、戻せば再利用されます。上限超過時は古い順に削除）。アプスケ不要な素材（長辺 3840 以上）のキャッシュはモデルによらず共通です。
- **同じ素材を別モデルで使う 2 クリップ**：モデルごとに別キャッシュを作り（①② の素材数に含まれます）、クリップごとに読み替えます（③ の差し替え表の `'@clips'`、`pyengine/mittler/engine.py` の `src_path`）。作品既定モデルのクリップは従来どおり素材パスで読み替えます。

### アップスケールなし（60fps だけ。2026-10-31）

アップスケールを行わず 60fps 化するだけの書き出しです。マスターの窓の「画質：標準」（タイムラインの `settings.master.upscale` に `"none"` を保存し、窓からの書き出し時は `--upscale none` も渡します）、単体では `mittler master … --upscale none` を指定します。

| 工程 | アニメ・実写（従来のマスター） | なし（60fps だけ） |
|---|---|---|
| ① アプスケ | 長辺が 3840 未満の素材を Real-ESRGAN で拡大 | **しない**（Real-ESRGAN 不要） |
| ② 補間 | アプスケずみを RIFE で 60fps 化 | 素材の**元の大きさのまま** RIFE で 60fps 化 |
| ③ 描く | キャンバス 2 倍（`ctx.scale`＝2）・60fps | キャンバス **1 倍**（通常の大きさ）・60fps |
| ④ 縮める | area で 1080 に縮小 | **無し**（出力＝タイムラインの大きさ。縦長作品もそのまま） |
| 書き出し前チェック | `scale_aware` の無いエフェクトで停止 | **止めない**（scale 1 のため不要）。`uses_fi`（コマ番号で絵が変わる）の注意は 60fps のため表示 |

詳細と実測：

- **適用される設定**：PC 設定の `scale`・`outHeight`（単体の `--master-scale`・`--master-out`）は使いません。`fps`（既定 60）・並列数・キャッシュ上限・RIFE の場所は通常どおりです。
- **キャッシュ**：補間ずみキャッシュ名は、アプスケ不要素材と同じ `<素材のハッシュ>_60_x264rgb10.mkv` です（アプスケしたものは `<ハッシュ>_<モデル>_60_…` になるため衝突しません）。同じ素材を同じ RIFE 引数で補間したものなので、4K マスターの「長辺 3840 以上の素材」の補間ずみキャッシュと相互に再利用されます（偽の道具で、「なし」のあとのアニメマスターが 4K 素材の補間を再実行せず MP4 も一致することを確認済み）。

|---|---|---|---|
| ① アプスケ | — | — | 30.2 秒 |
| ② 補間（① と重ねた残り） | — | 10.0 秒（VRAM +0.5 GB） | 19.1 秒（VRAM +3.5 GB） |

- **動作確認**：次の 2 コマンドが終了コード 0 で出力を生成することを確認し、続けて試し作品で `python -m mittler master` を試します。
  ```powershell
  realesrgan-ncnn-vulkan.exe -i <絵.png> -o <出力.png> -n realesr-animevideov3 -s 2
  rife-ncnn-vulkan.exe -0 <絵.png> -1 <絵.png> -o <出力.png> -m rife-v4.6
  ```
- **別の場所に置いた場合**：設定 `mittler.master.esrgan`・`mittler.master.rife`（単体は `--esrgan`・`--rife`）にそれぞれの exe パスを設定してください。
- **実測メモ**（作者の PC、RTX 3090、試し作品 6 秒：960×540 と 1280×720 の 24fps 映像 3 秒ずつ・キラキラ）：
  - RIFE の `-n`（目標コマ数）で 24→60 がそのまま出力されます（出力 i コマ目＝入力 i×24/60 コマ目の時刻。末尾 2 コマは最終コマを維持）。
  - 所要時間はアプスケ 15 秒（2 本・72 コマずつ）・補間 50 秒（4K で 72→180 コマずつ）・描く＋エンコード 28 秒（4K・60fps の 360 コマ）の合計 94 秒。2 回目はキャッシュ利用で 29 秒、MP4 は 1 回目と同一でした。
  - VRAM 増加は Real-ESRGAN 約 0.2 GB、RIFE（4K）約 3.3 GB（直列に実行するため同時には使いません）。
  - 旧形式キャッシュ（FFV1）では 4K・60fps 補間ずみが素材 1 秒あたり約 0.2 GB、アプスケずみが約 0.08 GB（細かい模様と粒の多い素材では補間ずみ 1 秒あたり 0.5 GB）。なお ①② は素材ファイル全体を通します（使用範囲のみではありません）。
  - 2026-10-30 夜から補間対象のアプスケずみを残さず、形式も H.264（RGB）にしたことで、同じ試し作品のキャッシュは 1.78 GB → 0.08 GB に削減されました（上の「マスター書き出しの既定値とキャッシュ」参照）。補間ずみは素材 1 秒あたり約 1〜80 MB（1344×768 の細かい模様・粒の素材で 80 MB）。偽マリアの映像素材（149 秒）全体で 4〜12 GB 程度の見込み（推測）。処理時間は従来とほぼ同じです（試し作品 1 回目 89 秒・2 回目 25 秒・`--fresh` 89 秒、2 回目と `--fresh` の MP4 は一致）。

### 動画1本を高画質にする（`mittler enhance`。作品は要らない。2026-10-31）

動画ファイルを 1 本渡すだけで、マスター書き出しと同じ処理で高画質化した MP4 を出力する同梱ツールです（タイムラインも作品フォルダも不要です）。

```powershell
tools\enhance.cmd <入力の動画> [<出力.mp4>] [--upscale anime|real|none]
python -X utf8 -m mittler enhance <入力の動画> [<出力.mp4>] [--upscale anime|real|none]   # pyengine フォルダで、描く python を使って実行
```

| `--upscale` | 処理内容 | 出力 |
|---|---|---|
| `anime`（既定。マスターで未指定時と同じ） | Real-ESRGAN（`realesr-animevideov3`）でキャンバス（出力の 2 倍。16:9 なら 3840×2160）へ拡大 → RIFE で 60fps 化 → area で縮小 | 短い辺 1080（16:9 なら 1920×1080、縦長 9:16 なら 1080×1920）・60fps |
| `real` | 上と同じ。モデルに `realesrgan-x4plus` を使用（写真・実写向け。約 11 倍低速） | 同じ |
| `none` | アップスケールしない。元の大きさのまま RIFE で 60fps 化（Real-ESRGAN 不要） | 入力と同じ大きさ（幅・高さが奇数なら 1 画素切り捨て）・60fps |

仕様と注意点：

- **出力パス**：省略すると入力ファイルの隣に `<入力の名前>_enhanced_<方法>.mp4` を出力します（同名があれば上書き）。
- **マスター書き出しとの共通性**：処理はマスター書き出しと同じ関数（`pyengine/mittler/master.py` の ①② `tools_pass`・道具確認 `missing_tools`、④ のエンコードコマンド `__main__.py` の `rgb_encode_cmd`・`vcodec`）を使います。同じ道具・引数（`-s` は足りる最小・`-j` は自動）・キャッシュ形式（`x264rgb10`）・縮小（area）・エンコード（`settings.export` の既定：libx264・medium・crf 18・yuv420p）で、③ 描く（エフェクト）だけがありません。その動画 1 本だけを置いた同サイズ作品をマスター書き出し（区間 1）したものと映像ストリームまで一致します（偽の道具で `anime`・`real`・`none` を確認済み）。
- **入力サイズ・fps・回転の判定**（すべてマスターと同じ）：
  - 長辺がキャンバス長辺以上（4K 動画など）の場合はアップスケールせず、60fps 化して 1080 へ縮小するだけです。
  - 60fps 以上の動画は補間しません（60fps より速い動画は 60fps へ間引きます）。
  - スマホの縦動画（回転メタデータ付き）は、回転後の向きでサイズを決めます。
- **音声**：入力の最初の音声ストリームが AAC・MP3・AC-3・E-AC-3・ALAC ならそのままコピー、それ以外は AAC 256k に変換します（マスターと同じ）。無音動画は無音のままです。
- **道具の場所**：Real-ESRGAN・RIFE はマスター書き出しと同じものを使います（上の「入れ方」参照）。既定の場所も同じですが（12 の表）、別配置の場合は環境変数 `MITTLER_ESRGAN`・`MITTLER_RIFE` または `--esrgan`・`--rife` で指定します（VS Code の設定 `mittler.master.*` は読みません）。必要なのに無ければ、開始前に「道具が無い」と名指しで止まります（`MASTER_STOP` の kind `tools`）。
- **`tools\enhance.cmd` の探索**：描く python（環境変数 `MITTLER_PYTHON` → PATH の `python`）と ffmpeg（`MITTLER_FFMPEG_DIR` → PATH）を探して `python -m mittler enhance` を呼び出します。
- **一時ファイルとキャッシュ**：出力フォルダに `_enhance_<番号>/` を作成し（コマの PNG とキャッシュ。4K PNG のため長い動画では数十 GB になることがあります）、完了・失敗・中断時に削除します。既定ではキャッシュを残さないため再実行時は ①② からやり直しになりますが、残したい場合は隠し引数 `--work <フォルダ>` を指定します（マスターの `work/master` と同じ形式で、次回は道具を呼ばず再利用。上限は `--cache-gb`）。
- **進捗と中断**：マスターと同じ `PHASE check`・`PHASE upscale`・`PHASE interp`・`PHASE render`・`PROGRESS <コマ> <全部> <秒>`、完了時に `MASTER_DONE {…}` と「できた：<出力>（大きさ・fps・コマ数・音・秒）」を出力します。中断は Ctrl+C か `<出力>.cancel` の作成です。異常停止（入力無し・読めない・道具無し・道具失敗）は終了コード 4 で `MASTER_STOP` と理由を出します。
- **所要時間の目安（推測）**：①② はマスターと同じ（作者の PC、偽マリア素材 1344×768・24fps で 1 秒あたり約 8 秒、実写の ① は 1 コマ約 2 秒）。④ は 4K→1080 縮小とエンコードのみで ③ が無い分、作品のマスター書き出しより高速です。**本物の道具ではまだ通していません**（2026-10-31 時点は偽の道具のみ）。
- **隠し引数（通常は不要。意味はマスターと同じ）**：`--esrgan`・`--rife`・`--rife-model`・`--master-scale`・`--master-fps`・`--master-out`・`--down`・`--cache-fmt`・`--esrgan-j`・`--rife-j`・`--work`・`--cache-gb`。

### マスター書き出しの並列（この PC での目安と決め方。2026-10-31）

以下の記載における「作者の PC」は Ryzen 9 9900X（12 コア 24 スレッド）・メモリ 61.6 GB・RTX 3090・NVMe、「ノート PC」は 16 スレッド・メモリ 31 GB・GPU なしの環境です。

すべて**自動**で決定されるため設定は不要です。CPU の論理プロセッサ数と ③ 開始時の空きメモリから算出するため、どの PC でもそのまま動作します。

- **絵の同一性**：道具が出力する PNG は `-j` によらずバイト単位で一致し、キャッシュの中身（映像パケット）は前の版と同じ、通常書き出し（`mittler video`）も前の版と 1 ビットも変わりません。マスターの MP4 は区間の切り方で x264 の結果が変わります（前の版でも並列数を変えると MP4 が変わりました）が、区間数は並列数によらず範囲の長さだけで決めるため、並列数や OpenCV のスレッド数を変えても同じ MP4 になります。

| 対象 | 自動の決め方（`pyengine/mittler/master.py`） | 作者の PC | ノート PC（16 スレッド・31 GB） | 手動で変える場合 |
|---|---|---|---|---|
| ① Real-ESRGAN の `-j`（PNG 読込:GPU:PNG 書出） | `tool_threads`：読込 `CPU÷8`（1〜2）・GPU 既定の 2・書出 `CPU÷3`（2〜8） | `2:2:8` | `2:2:5` | 単体の `--esrgan-j 2:2:8` |
| ② RIFE の `-j` | `tool_threads`：読込 `CPU÷3`（1〜8）・GPU 2・書出 `CPU×2÷3`（2〜16） | `8:2:16` | `5:2:10` | 単体の `--rife-j 8:2:16` |
| ①② の重ね方 | `tools_pass`：素材 i の補間と素材 i+1 のアプスケを同時に実行（同じ道具は 1 本ずつ。GPU 上は ESRGAN 1 本と RIFE 1 本まで、VRAM は従来の最大＋約 0.2 GB） | 同じ | 同じ | なし |
| ③ 並列の数 | `render_jobs`：`CPU÷2` と `（空きメモリ−4 GB）÷2.5 GB` の小さいほう（1〜16） | 12 | 4〜8（空きメモリ次第） | マスターの窓の詳細設定「同時処理数」（空＝自動）・単体の `--jobs` |

| ③ OpenCV のスレッド | 絞らない（OpenCV の既定） | — | — | 単体の `--threads N` |

#### 実測データ（作者の PC、偽マリアの読み取り専用コピー、実道具の Real-ESRGAN・RIFE）

- **道具単体（偽マリア素材 1344×768・96 コマ）**：Real-ESRGAN（×3）は既定 `-j 1:2:2` の 24.2 秒 → `2:2:8` で 7.3 秒、RIFE（4K・96→240 コマ）は 54.1 秒 → `8:2:16` で 12.2 秒に短縮しました。既定値では PNG 読み書きが詰まり GPU が 2〜3 割しか稼働していませんでした。RIFE の GPU スレッド（proc）を 4 にしても速くならず VRAM のみ増える（5.1 → 8.4 GB）ため 2 のままとしています。
- **③ の並列数（14〜20 秒・360 コマ、区間＝並列数の旧方式）**：全体時間は並列 4 で 466 秒・8 で 404 秒・12 で 391〜395 秒・16 で 373〜398 秒でした。16 並列はメモリだけが増え（自プロセス合計 28 → 37 GB）、24 並列はメモリ不足に陥りました（PC 全体で 64.6 / 66 GB、`.cancel` も 150 秒以上届かず）。1 プロセスあたり 2.2〜2.5 GB（描く python 0.4〜1 GB＋縮小・エンコード ffmpeg 約 1.3 GB）を使います。
- **③ の区間分割**：区間＝並列数の旧方式では末尾に重い数区間を待つだけの時間が長く発生していました（14〜26 秒・並列 12 で 945 秒のうち約 200 秒、CPU 82% → 10〜20%）。区間 30 に増やすと 888 秒に短縮しました。
- **③ のボトルネック**：エフェクト計算（4K 光ブルームのガウスぼかし σ 28・80 px、色の手直し、前のリリックなど。1 プロセス 1 コマ約 3.2 秒のうち光が 1.7 秒）で CPU が詰まります。全プロセス稼働中の速度は並列 4 からほぼ横ばいです（58〜70 秒：並列 4 で 0.857、12 で 0.876 コマ/秒。並列 4 でも OpenCV が 1 プロセス内で CPU を使い切っているため）。高速化の多くは区間細分化による末尾待ち削減分です（12 秒範囲で 1.18〜1.26 倍）。GPU は ③ では使用していません。さらに速くするにはエフェクトの描き方自体を変える必要があります（縮小画像にぼかしをかける・GPU 描画するなど。絵が変わるためユーザーが判断します）。
- **OpenCV のスレッド制限**：区間ごとに 2・1 へ絞ると、並列 12・区間 30 で無制限 875 秒に対して 2 で 888 秒、並列 16・1 では 1723 秒（CPU 使用率 67% 止まり）と逆効果だったため、既定は無制限です。
- **PNG 圧縮レベル**：② の前の 4K コマ取り出しは PNG 圧縮レベルを 3 にしました（ffmpeg 既定より軽く、可逆のため絵は同一）。4K・96 コマで 5.4 → 3.6 秒に短縮し、RIFE の読み込み時間・出力とも変化ありませんでした。

偽マリア 14〜26 秒（素材 3 本・301 コマ → 4K・60fps の 720 コマ）をキャッシュ無しから最後まで実行した比較（実道具）：

| 工程 | 前の版（`05d876f`、並列 4） | 今の版（全自動：並列 12・区間 24） |
|---|---|---|
| ① アプスケ（3 本） | 88 秒（GPU 平均 21%） | ①② を重ねて合計 99 秒（GPU 平均 36〜71%） |
| ② 補間（3 本、4K で 301 → 752 コマ） | 222 秒（GPU 平均 17%） | （上に含む） |

- ピークメモリ（PC 全体）は 28.7 → 40.9 GB、VRAM はデスクトップ使用分の上に最大約 3.6 GB（前は 3.4 GB）。キャッシュの中身は同一（映像パケットが一致）。

## 14. 3D（なくてもよい。3D のエフェクトを使う作品だけ。2026-11-13）

3D の演出には 2 通りあります。どちらも 3D エフェクトを使う作品にだけ必要です（3D を使わない作品は、何も追加しなくても従来どおり動き、絵も 1 ビットも変わりません）。

| 項目 | GPU の 3D（moderngl） | Blender の 3D |
|---|---|---|
| エフェクト | `gl_cards3d`（3D の板）・`gl_particles3d`（奥行きのある粒子）・`gl_lightrays`（光の筋） | `blender3d`（Blender で描いた場面を重ねる） |
| 描き方 | その場で GPU（OpenGL 3.3）で描画。1 コマ数十ミリ秒 | Blender で描いて作品の `work/3d/` にためて再利用。書き出し時は区間の前にまとめて描画 |
| 入れるもの | 描く python に `setup/requirements-3d.txt`（moderngl・glcontext） | Blender（blender.org の公式配布物・LTS） |

### 入れ方

導入するかどうかは PC の持ち主が決めます（エージェントは必ず事前に伝えて OK をもらってから実行してください）。

1. **moderngl**：描く python（`mittler.render.python` の venv）に足すだけです（ほかのパッケージは変わりません）。
   ```powershell
   <venv>\Scripts\python.exe -m pip install --only-binary=:all: -r <mittler>\setup\requirements-3d.txt
   ```
   作者の PC では `moderngl` 5.13.0・`glcontext` 3.1.0（Python 3.14 の wheel。SHA-256 は `317010ee…`／`ec2f1678…`）で動作確認済みです。
2. **Blender**：<https://download.blender.org/release/> から LTS の **zip（ポータブル版。インストーラーではないもの）** を取得し、同じ場所にある `blender-<版>.sha256` と照合（`certutil -hashfile <zip> SHA256`）してから任意の場所へ展開します。
   - 作者の PC で確認済み：Blender 5.2.4 LTS（zip の SHA-256：`bbd78f89…c967c`）。
   - VS Code の設定 `mittler.blender.path` に `blender.exe` のパスを書きます（12 の表）。
   - アドオンや追加ツールは不要です（`--factory-startup` で起動します）。
3. **確認**：`python setup\mittler_setup.py` で「3D のエフェクト（GPU の 3D・moderngl）」「Blender の 3D」が `[OK]` になることを確認します。詳しく確認する場合は、描く python で次を実行します（試し作品を自動生成し、描画・同時刻一致・中断を検証）。
   ```powershell
   python -X utf8 tools\smoke_3d.py --require-gl --blender <blender.exe>
   ```

### GPU とセッションの注意

- **moderngl が使う GPU**：OS とドライバーが決めます。作者の PC（RTX 3090 と CPU 内蔵 GPU）では、**画面のあるセッション（VS Code）は画面がつながっている GPU、画面の無い ssh セッションは AMD の内蔵 GPU（OpenGL 4.3）** が選ばれました（どちらも描画可能）。OpenGL 3.3 が使えない環境（「GDI Generic」＝CPU の GL 1.1 のみのセッションなど）では、3D エフェクトのある時刻で「3D の描画が使えない（理由）」と停止します（黙ってスキップしません）。
- **Blender のレンダラー**：Cycles は CUDA／OptiX（NVIDIA）で描きます（画面の無いセッションでも同じ）。EEVEE は OpenGL で描きます（作者の PC では ssh セッションでも RTX 3090 で描画できました）。クリップの `device` は既定 `auto`（OptiX → CUDA → HIP → CPU）です。
- **GPU の占有**：長い書き出しの Blender は GPU を使い続けます。ほかの人が同じ PC の GPU を使っているときは、短い区間ずつ実行してください。

### 3D のある作品の例外

- GPU で描く絵は、別の PC・別の GPU・別のドライバーでは画素値がわずかに異なることがあります。
- 同じ PC・同じ設定であれば、同じ時刻は常に同じ絵になります（静止画・プレビュー・書き出し・並列数によらず一致することを `tools/smoke_3d.py` で確認）。
- Blender の Cycles を GPU で描き直すと、同じ設定でも数画素が 1〜6 異なることがあるため（作者の PC で実測）、Blender の絵は**ためた絵を使い回す**ことで一致させています（ためた絵を消すと、次回描画時は少し異なる絵になりえます）。

## 15. 前からの作品を、絶対パスを書かない形にそろえる（しなくても動く。2026-11-13）

2026-11-13 より前に作った作品は、作品内のファイルが Mittler の場所を絶対パスで参照しています（フックの `python "<mittler>/tools/mittler_state.py"`、`CLAUDE.md` の `@<mittler>/docs/スターターガイド（AI用）.md`、本文中の `<mittler>\tools\mittler_api.py` など）。

**そのままでも、その場所に Mittler（リポジトリ）がある限り動作します**（配布版に入れ替えても、リポジトリを消さなければ動きます。Mittler が作品ファイルを勝手に書き換えることはなく、開けば `.mittler/` に `env.json` と中継スクリプトを書き出します）。

別 PC へ移す・リポジトリを消す・人に渡す前に新しい形式へそろえる場合は、作品ごとに次の手順を行います（実行前に作品フォルダで `git add -A` し、編集画面は閉じておいてください）。

1. 新しい版の Mittler で作品を 1 度開きます（状態フォルダに `hook.py`・`guide.md` などが書き出されます）。
2. フックを現在の形式に書き直します（`--dry-run` で先に確認できます）。
   ```powershell
   python <mittler>\tools\fix_hooks.py <works>\<作品>
   ```
3. `CLAUDE.md` の `@<…>/docs/スターターガイド（AI用）.md` の行を `@.mittler/guide.md` に変更します。新しいひな形（`templates/project/CLAUDE.md`・`AGENTS.md`）に合わせて、本文を `AGENTS.md` へ移しても構いません。
4. 本文中に書かれた Mittler の場所を次のように置き換えます。
   - `python <mittler>\tools\mittler_api.py <作品> …` → `python .mittler/api.py . …`
   - `python -m mittler stills …`（pyengine のフォルダで）→ `python .mittler/engine.py stills …`
   - `<mittler>\docs\…` → 「`.mittler/env.json` の `docs_dir` の中の …」
5. 修正後、作品フォルダで Claude Code を起動して話しかけ、編集画面の今が添えられることとガイドが読まれていることを確認します。
