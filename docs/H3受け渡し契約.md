# H3 受け渡し契約（Mittler ⇔ H3）

Mittler の動画化（動画化予定のクリップ）と、動画生成の H3（MiniMax H3 のキュー）との間における**受け渡し形式の正本**です。

- **H3 側と取り決めた受け渡し用の名前**（Mittler 側だけでは変更しません）：素材フォルダ名 `claude-cut-h3/`、`<project>` の先頭 `cc_`、依頼 YAML の先頭行 `# claude-cut の 🎬 動画化…`
- **Mittler 側の名前**：環境変数 `MITTLER_MYDRIVE`・`MITTLER_H3_ROOT`、補助コマンド `tools/mittler_api.py`

Mittler と H3 の関係は、次の 2 点のみです。

1. **ジョブと依頼ファイルを書く**：素材フォルダに入力（絵・声）をコピーし、inbox に依頼の YAML を置きます。
2. **出来上がった動画を受け取る**：outbox の結果を確認し、完成した動画を作品にコピーします。

> **ランナーは外部。契約はこのファイルの形式のみ。**
> H3 のランナー（実際に生成を行う側。現在は Colab で動作）は Mittler の外にあり、Mittler はランナーの場所も起動方法も知りません（起動・制御せず、ファイルを置いて待つだけです）。
> ランナーを別に作り直す場合でも、このファイルの形式を守れば Mittler はそのまま使えます。

Mittler の中で H3 の決まりを持っているのは **`tools/h3_jobs.py` の 1 か所だけ**（H3 のアダプタ）です。
編集画面のサーバー（`server/server.js`）はエンジンに依存しない処理（参照の解決、声の参照の場所と長さの取得、出力ファイル名・シード・ジョブの ID と状態の管理）だけを行い、ジョブを作成するときに `python tools/h3_jobs.py build` を呼び出します ✅ `server/server.js:247-295`。
（2026-10-30 以降、サーバーとジョブ係は `tools/h3_jobs.py` を直接名指しせず、エンジンとアダプタの対応表 `tools/engines.json` から参照します。詳しくは 13 章「エンジンを足すには」を参照してください。）

根拠の行番号は、「H3の決まりをアダプタへ移動」のコミット（`971964c`）時点のものです。

## 3. 流れ

```
編集画面「動画化」／mittler_api.py video
  → サーバー（createVideoJob）：参照を開き、声の参照・出力の名前・シードを決めて、
       アダプタ python tools/h3_jobs.py build（H3 の決まりを当てる。頼めないものは止める）→ ジョブ work/jobs/job_*.json（state: queued）
  → ジョブ係 tools/jobs.py → tools/h3_jobs.py submit：
       ① 素材フォルダ <マイドライブ>/claude-cut-h3/<project>/<id>/ に絵・声を写す
       ② 依頼の YAML を素材フォルダに書き（控え）、同じ中身を <H3_tasks>/inbox/<project>__<id>.yaml に置く（state: waiting「H3 の順番待ち」）
  → （Mittler の外）H3 のランナーが inbox を読んで生成し、outbox に結果を置く
  → ジョブ係 tools/h3_jobs.py poll（20 秒ごと）：
       <H3_tasks>/outbox/<project>/<id>.error.txt があれば failed
       <id>.result.json があれば、動画を作品の assets/videos/gen/<id>.mp4 に写して done
  → 編集画面がジョブの結果を予定クリップの動画のテイクに入れる（applied）→ ユーザーが「採用」で映像トラックへ
```

根拠 ✅ `server/server.js:247-295`・`tools/h3_jobs.py:93-176,201-285`・`tools/jobs.py:144-157`・`editor/plan.js:143-168`。

## 5. 依頼の YAML `<H3_tasks>/inbox/<project>__<id>.yaml`

### 書き方

- **文字コード・改行**：UTF-8（BOM なし）。改行は Python の `write_text` の既定（Windows では CRLF。実物も CRLF） ✅ `tools/h3_jobs.py:236-237`。
- **先頭コメント（1〜2 行目）**：`# claude-cut の 🎬 動画化（tools/h3_jobs.py が置いた）` および `# 作品: <作品のフォルダ>  クリップ: <予定クリップの id>` ✅ `tools/h3_jobs.py:231`。
- **キーと値の形式**：1 行に 1 つ `キー: 値` で書きます。**値は JSON 形式**（`json.dumps(…, ensure_ascii=False)`。文字列は `"…"`、改行は `\n`、配列は `[…]`）です。JSON は YAML としてもそのまま読めます ✅ `tools/h3_jobs.py:179-181,232`。
- **配置手順**：素材フォルダに `.part` で書き込み、控えを出力してから `os.replace` で inbox へ移動します（ランナーが書きかけのファイルを読まないようにするため） ✅ `tools/h3_jobs.py:235-244`。
- **キーの並び順**：下の表の順に出力します（上書きキーは既存のキーならその位置を上書きし、無ければ末尾に追加します）。

## 6. プロンプト（`prompt`）の組み立て

動画のプロンプト（予定クリップの `video.prompt`）の `@import` をサーバーが展開したあと（`server/plan_refs.js`）、アダプタが次の手順で組み立てます。

1. **6節の形**（本文に `subject_definitions:` を含む。大文字・小文字は問わない）の場合：
   - **本文を書いたとおりにそのまま送ります**（下の 2・3 は行いません）。
   - 警告「6節の形（…）なので、プロンプトは書いたとおりに送った（…）」を出します ✅ `tools/h3_jobs.py:37,146-149`。
2. それ以外の場合：
   - 本文、キャラの外見（ある場合：`人物：` と `<別名>：<外見>` の行）、画風（`style(…)` の文）を空行でつなぎます ✅ `tools/h3_jobs.py:142-143,150-151`。
3. ref2va で 6節の形でない場合、先頭に次を追加します ✅ `tools/h3_jobs.py:152-155`：
   - `<Picture 1> is the exact first frame.`
   - 参照画像ごとに `<Picture N> is <別名>（参照）.`（N は 2 から連番）
   - `<Audio 1>: fully_copy - the voice of the speaking character. Mouth movements are precisely synchronized with <Audio 1>.`

## 7. 上書きできるキー（`H3_KEYS`）と既定値

H3 の既定値と制限値は、すべて `tools/h3_jobs.py` の先頭（`H3_KEYS`・`FPS`・`MIN_FRAMES`・`FL2V_STEP`・`VOICE_MIN`・`REF2VA_MAX_REFS`・`REF2VA_DEFAULTS`・`DRAFT_STEPS`・`SIX_SECTIONS`・`MYDRIVES`）にまとめてあります ✅ `tools/h3_jobs.py:26-38`。

- **上書きできるキー**：予定クリップの `video.h3`（例：`{"steps": 20, "seed": 123}`）に書かれたキーのうち、`steps`・`scheduler`・`ref_image_size`・`seed`・`fit`・`gen_seconds`・`lyrics`・`sing_start`・`sing_end` だけを YAML に追加します（それ以外のキーは破棄します） ✅ `tools/h3_jobs.py:27,228-230`。
- **ref2va の既定値**：`ref_image_size: "max"`・`scheduler: "beta"`・`steps: 25`（顔の崩れ対策。ref2va の成功例どおり）。`video.h3` で上書きできます ✅ `tools/h3_jobs.py:35,226`。
  - ref2va の成功例および `lyrics`・`sing_start`・`sing_end` の使用例は `docs/技術集/07b_口パク_ref2va_話者の指定と成功例.md` を参照してください。
- **fl2va の既定値**：Mittler 側からは追加しません（ランナーの既定値を使用します）。
- **下書き**（編集画面の「下書き」、または `mittler_api.py video --draft [--steps N]`）：`steps` を N（既定 10、4〜40 の範囲に収める）にします。シードは本番と同じ値を使います ✅ `tools/h3_jobs.py:36,164-167`。
- **シード**：5 章の表の `seed` のとおり、下書きも本番も同じ値になります。シード値の決定はサーバー側で行います（エンジンに依存しません） ✅ `server/server.js:273-274`。

## 8. 結果 `<H3_tasks>/outbox/<project>/`

ジョブ係が 20 秒ごとに確認します（ジョブの `last_poll` を更新） ✅ `tools/h3_jobs.py:26,249-266`。確認の優先順位は次のとおりです。

1. ジョブが止められていれば（`cancel`）、ほかの確認はせず `cancelled` にします（9 章）。
2. `<id>.error.txt` があれば `failed` にします。中身の末尾 1500 文字を `H3：…` の形式でジョブの `error` に書き込みます ✅ `tools/h3_jobs.py:260-263`。
3. `<id>.result.json` があれば読み込みます（無ければ待機を続けます）。Mittler が参照するのは次のキーだけです。

| キー | 使い方 | 根拠 |
|---|---|---|
| `outputs` | 文字列の配列。**Colab のパス**（`/content/drive/MyDrive/…`）を `<マイドライブ>/…` に読み替え、拡張子が `.mp4` で名前に `_lipsync` を含まず、この PC に同期済みのもののうち最初の 1 つを使用 | `tools/h3_jobs.py:268-273` |
| `settings.frames`・`settings.fps` | 動画の長さ＝`frames ÷ fps`（`fps` が無ければ 24）。`frames` が無ければジョブの `seconds` を使用 | `tools/h3_jobs.py:281-284` |
| `settings`・`seconds_h3`・`warnings` | そのままジョブの `result.h3` に保存（テイクには入れない） | `tools/h3_jobs.py:284` |

- **Colab パスの読み替え**：文字列から `/content/drive/MyDrive/` を取り除き、`<マイドライブ>` からの相対パスとして解決します ✅ `tools/h3_jobs.py:270-271`。
- **動画の同期待ち**：結果ファイルはあるのに動画ファイルがまだ Google ドライブから届いていない場合、`note` に `結果はあるが動画がまだ Drive に来ていない` と書いて待機を続けます ✅ `tools/h3_jobs.py:274-276`。
- **完了処理**：動画は作品の素材ルートの `assets/videos/gen/<id>.mp4` へコピーし（`shutil.copy2`）、状態を `done`、結果を `result: {src, dur, h3}` とします ✅ `tools/h3_jobs.py:277-285`。
- **後処理**：outbox および inbox のファイルは、Mittler からは削除も移動も行いません。

## 9. 止める（キャンセル）

- **キャンセル要求**：編集画面の「止める」または `POST /api/jobs/<id>/cancel` により、ジョブに `cancel: true` を書き込みます ✅ `server/server.js:752-758`。
- **inbox 配置前（`queued`）**：inbox に置かずに `cancelled` にします ✅ `tools/jobs.py:136-137`。
- **inbox 配置後（`waiting`）**：ジョブを `cancelled` にしますが、**置いた依頼はそのまま残ります**（inbox やランナーには通知しません。ジョブの `note` に「H3 に置いた依頼は残るため、運用担当へ連絡してください」と記録します） ✅ `tools/h3_jobs.py:257-259`。生成そのものを止めたい場合は、H3 の運用担当者に連絡してください。

## 10. dry（確かめるだけ）

編集画面の `window.MITTLER_PLAN_DRY` または `mittler_api.py video --dry` で実行します。

- 素材フォルダに絵・声・控えの YAML までを作成し、**inbox には置きません**。
- ジョブは `failed`（理由：`dry（inbox に置いていない）`）となり、`h3: {yaml, fields}` に生成内容を記録します ✅ `tools/h3_jobs.py:239-242`。

## 11. テスト（ランナーなし）

`tools/smoke_plan.py --phase 4|5 --fake-drive <一時フォルダ>` で、本物の `H3_tasks` とランナーを使わずに一連の流れを検証できます。

- サーバーの `MITTLER_MYDRIVE`・`MITTLER_H3_ROOT` を一時フォルダに向けて起動します。
- 模擬 H3（`smoke_plan.py` の `mock_h3`）が、アダプタにより inbox に置かれた YAML を読み取り、この契約の形式どおりか（キー、並び順、素材フォルダのファイル、控え、ref2va の既定値）を検証します。
- outbox に模擬の `result.json`（`outputs` は Colab のパス形式）と動画ファイルを配置します。
- テイク反映 → 採用 → キャンセル（置いた依頼が残ることの確認）までを通してテストします。

## 13. エンジンを足すには（生成の差し替え口。2026-10-30）

動画化予定の生成（動画化、開始・終了の絵）は、エンジンごとの**アダプタ**が固有の決まりを持ちます。サーバーとジョブ係はエンジン名からアダプタを引くだけで、エンジン固有の決まりは持ちません。

### 対応表とジョブのエンジン

- **対応表（1 か所）**：`tools/engines.json`
  - `engines`：`{"<エンジン>": {"kind": "video"|"image", "adapter": "<tools/ の下のファイル名>"}}`
  - `default`：種類ごとの既定エンジン
  - 現在の登録は H3（`h3-fl2va`・`h3-ref2va` → `h3_jobs`）と Codex（`codex` → `codex_jobs`、絵）の 2 つです。
- **ジョブのエンジン**：
  - 動画化：クリップの `video.engine`（無ければ `default.video`）→ ジョブの `video.engine`。
  - 絵：クリップの `start_frame.engine`／`end_frame.engine`（無ければ `default.image`）。既定と同じときはジョブに書かず（従来と同じジョブ JSON 形式）、既定と異なるときだけジョブの `image.engine` に書き込みます。

### アダプタの型（`tools/<adapter>.py`）

標準ライブラリのみで実装し、ジョブ係の Python で動作させます。

| 要素 | 呼び出し元 | 中身 |
|---|---|---|
| `build(q)` と `python tools/<adapter>.py build` | サーバー（`server/server.js` の `adapterBuild`。ジョブ作成時） | 標準入力からエンジン非依存の依頼（参照を展開済みのもの）を受け取り、標準出力に 1 行の JSON `{ok, video\|image, sent, warnings}`（絵は `sidecars` も含む）または `{ok: false, error}` を返す。依頼できないものはここで止める（理由は編集画面に表示） |
| `submit(runner, p, job)` | ジョブ係（`tools/jobs.py`。`state` が `queued` のジョブ） | 生成を依頼する。完了まで待つエンジン（Codex）はここで `done`／`failed`／`cancelled` まで進め、キューに積むエンジン（H3）は `waiting` にして返す |
| `poll(runner, p, job)` | ジョブ係（`state` が `waiting` のジョブ） | 結果を確認し、完成していれば作品にコピーして `done` にする（待たないエンジンは何もしない） |
| `SUBMIT_ERROR` | ジョブ係 | `submit` の例外をジョブの `error` にする際の先頭文言（`None` ならジョブ係外のエラーとしてログに書き残し、次回に再試行する。Codex は従来からこの扱い） |

- `runner` はジョブ係のインスタンス（`update(p, **kw)` でジョブ JSON を更新、`log(…)`、`read(p)`、`jobs`（`work/jobs`）、`project`）、`p` はジョブ JSON のパスです。
- 依頼 `q` の内容は各アダプタの `build` の説明（H3：`tools/h3_jobs.py`、Codex：`tools/codex_jobs.py`）を参照してください。
- サーバー側に残す責務は、参照の展開・出力ファイル名（`_t<n>`）・シード・ジョブの ID と状態の管理だけです。

### 追加手順

1. `tools/<新しいアダプタ>.py` を上の型に従って実装します。
2. `tools/engines.json` に登録します。
3. 編集画面で選択できるようにする場合は、`editor/plan.js` の `ENGINES`（動画化の選択肢）に追加します（ID が `engines.json` に存在することは `tools/smoke_same.py` が検証します）。
4. 受け渡しの形式をこの文書のようにまとめます。
5. 本物を動かさないテストを用意します（H3 は模擬の inbox/outbox＝11 章、Codex は偽の codex で依頼内容を記録する方式）。

### Codex のアダプタ（`tools/codex_jobs.py`）の決まり

- 参照画像は 5 枚まで（`image_gen` に渡せる上限）。
- プロンプトの末尾に「【画面】横 W × 縦 H …」の行を付与します。
- 作品ごとの Codex セッション（`work/codex-session.json`）と、出力ファイルの横の `<出力>.codex.json`（`sidecars`）を扱います。
- 生成実体は `tools/gen/codex_image.py`（同時実行 1 件、停止は `cancel`）です。
- Codex CLI の場所とモデルは PC 設定の `mittler.codex.path`・`mittler.codex.model` で指定します（ジョブ係へ環境変数 `MITTLER_CODEX`・`MITTLER_CODEX_MODEL` で渡します。未設定時は PATH 上の `codex` と `gpt-6.1-sol` を使用。詳しくは `docs/インストールガイド.md` の 12）。
